# AI model and effort selection

This file is the record of which model and effort each Claude call uses, why, and what has been measured. Read it before testing any call again: a call marked **Proven** needs no re-test unless the re-test triage below (Policy) calls for one.

Settings live in code:

- Background tasks: `electron/ipc/claudeTaskProfiles.js` (`CLAUDE_TASK_PROFILES`).
- Application stages: `electron/ipc/careerWritingCore.js` (`APPLICATION_STAGE_PROFILES`); stages not listed there default to Sonnet high (`CLAUDE_APPLICATION_MODEL`/`EFFORT` in `claudeApplicationRunner.js`). Every call names its own stage: a call that borrows another stage's profile is not proven by that stage's test (found 2026-11-12, when four interview calls ran on `qa-brief` or `qa-fact-*` without a test of their own).
- Interview Helper stages, live calls and the practice call (`qa-*`, `typed-job-*`, `career-file-to-text`, `practice-call-plan`, the Listen matcher and the practice call opener, main reply and classifier): moved to the separate Interview Helper repository on 2026-11-18. Their rows and measured results below are kept as history; their profiles and code no longer live here.
- DeepSeek routing: `electron/ipc/aiCallProviders.js` (`application:` and `task:` keys; the one `qa:` entry moved with Interview Helper). The 2026-11-07 measurements are in `docs/application-improvement-sessions.md` (Hard rules); the 2026-11-15 ones are in this file's rows.

## Policy

**Hard exclusions.** Never use `max` effort, for Claude or for DeepSeek reasoning. Never use Fable. Always use the latest model: the Claude family alias (`haiku`, `sonnet`, `opus`) resolves to the newest model, and DeepSeek uses the newest Flash and Pro the provider maintains. Never test or pin an older version.

**Candidate models.** Every ladder for a call that is not live includes the latest **DeepSeek Flash** and **DeepSeek Pro** next to Claude Haiku, Sonnet and Opus. Each DeepSeek model is tested with reasoning off and with reasoning on at low, medium and high effort; only `max` reasoning is excluded. DeepSeek is usually by far the cheapest (Flash with reasoning off cost about $0.001 a call on requirements-audit, against $0.058 for Claude), so it sits at the bottom of the cost order and is tried first. It runs through `electron/ipc/aiCallProviders.js` routes (`deepseek-flash`, `deepseek-pro`) and `offloadTextCall`. A DeepSeek route needs Offload credit. **No fallback for worker tasks and interview calls (the owner's rule, 2026-11-15):** a call routed to DeepSeek is never answered by Claude instead. When credit runs out the task worker pauses with `OFFLOAD_CREDIT_EXHAUSTED`, keeps the queued work, shows the pause in the dock and retries on Resume or every 10 minutes; an interview call fails with that code. Any other DeepSeek failure is shown as a failed attempt and retried on DeepSeek, and a rejected answer is corrected by DeepSeek again. The same holds inside an application bundle (`requirements-audit`): a DeepSeek failure fails the stage with its `OFFLOAD_*` code, the bundle stops with its saved progress, and Retry runs the stage on DeepSeek again. Limits measured 2026-11-07: the app caps DeepSeek output at 32k tokens, so reasoning settings truncate long answers, and web research only works through Offload's built-in `web_search`/`web_fetch` (`webTools`). Calls that use tools other than web search, page images, or truth checks (fact-check stages, `qa-research`, `typed-job-research`) are not routed to DeepSeek. Live calls also include DeepSeek in their speed tests: the 2026-11-07 Listen-matcher test found Flash slower than Opus medium.

**Calls that are not live** (everything except the calls that run while a practice or real interview is happening): use the cheapest setting whose quality is within noise of the best setting tested. Find it like this:

1. Order candidate settings by **measured** cost per call, cheapest first. Do not assume model-tier order: on input-heavy prompts Sonnet low cost about the same as Opus xhigh (editorial planner, 2026-11-09).
2. Test the cheapest setting on the hardest few real prompts first. Pass means: the app's own validator accepts it at about the production first-try rate, and a blind judge (or planted defects, for audits) finds it within noise of the reference.
3. Stop climbing at the first setting that passes, and confirm it on all captured prompts with a second run. If the confirmation fails, go up one step.
4. A setting that needs more retries counts its retry cost. Generation time is not a criterion.
5. Measure the noise floor: run the reference setting twice, or include an unchanged rerun as a control arm. A gap smaller than that is not a difference.
6. For a stage whose output feeds another stage (planner to writer, compile to audits), judge the downstream result too, not only the stage's own output.
7. **Every call is proven by a test (the user's rule, 2026-11-10).** A call's setting is settled only by measurement, never by its annual spend being small. The cost-bound shortcut used until 2026-11-10 is withdrawn; calls it covered are marked **Needs test**. Running on the cheapest setting that exists (Haiku low) is not proof either: such a call still needs one comparison against a stronger setting (**Needs quality check**). Keep tests proportionate to the call: the smallest replay or arm that answers the question.

**Live calls** (practice-call opener, main reply and classifier; the Listen matcher during a real interview): use the fastest setting, measured by p95 first-word or first-sentence time under realistic load, among settings that meet the call's quality floor (rule-following or correctness measured on real cases). A setting that is faster but breaks the call's rules is not eligible. When the speed difference is insignificant but the quality loss is significant, choose the better-quality setting (the user's rule, 2026-11-09). "Insignificant" means within run-to-run timing noise or a small fraction of the call's latency budget; for example 0.2 s at p95 on a 2 s reply.

**Re-test triage (adopted 2026-11-21; replaces the earlier rule that any changed prompt, schema or validator triggers a re-test).** A test runs only when a change can plausibly move the choice.

1. **Baseline per call.** Every row in Results by call records its **Baseline**: the commit of the call's prompt-building code (prompt, schema, validator, tools) when it was last tested, and which recorded prompts that test used. For a row tested before this rule, it is the commit current on the row's test date (`git log --before=<date>` on the call's files). Where it cannot be determined the row says "unknown", and the next change to that call is treated as level 2. A row never tested says "none (untested)".
2. **Compare with the baseline, never with the previous revision.** When a call changes, assess the whole difference since its baseline (`git diff <baseline>..HEAD` over that call's prompt, schema, validator and tool files). Compare the instructions and output rules, not the per-call data. Small changes add up: after original → rev1 → rev2, rev2 is assessed against the original.
3. **Pick a level from that diff** and record it in the Log with a one-line reason:
   - **Level 1, no test:** the change cannot plausibly move the choice: wording, examples, reordering, a rule the host enforces in code, more of the same input, host bug fixes, renames. The baseline does not move.
   - **Level 2, regression check:** the task got somewhat harder: a new strict output rule (exact copy, IDs or quotes), a stricter validator, noticeably longer input. Run only the current setting, once, on stored prompts, through the app's own validator, and compare with stored production answers. Pass: the baseline moves to the current commit. Fail: go to level 3.
   - **Level 3, full ladder:** the change could plausibly move the choice either way: a new task, a new judgement or output type, a new kind of input (images, a new evidence source), tools added or removed, the call moving between live and not live, a changed latency budget. Ladder as How to measure describes. The baseline moves when the new choice is recorded.
   - When unsure, use level 2.
4. **Direction matters.** A change that makes the task easier only warrants testing whether a cheaper setting now passes, and only for a call that is expensive or runs often. A change that makes it harder starts with a level 2 regression check.
5. **Unchanged rules.** A call that has never been tested still needs its first test; a setting chosen by analogy stays a placeholder. A new model release follows the New model release playbook. A new candidate provider is laddered as Candidate models describes. A production signal (quality drift, rising retries or rejections) goes straight to level 2, whatever the diff says.

**Results are tied to model versions.** The app always calls the latest alias, but every result here was measured on a specific version, listed under Model versions tested. When a newer version of any family is released, the earlier results for that family are history. A call whose ladder included that family gets a new assessment on the new version; do not assume the old ranking carries over. Calls whose ladder never involved that family are unaffected. Record the resolved model id with every new result. The Claude stage runners return it as `model`, and the ladder tools write it to each result row.

## How to measure

**Every run records itself as it goes (rule since 2026-11-10).** On 2026-11-09 a session ran out of usage mid-ladder and was then deleted; its result rows lived only in the session scratchpad, so measured pick results were lost. Now:

- Each test tool writes its run to [`docs/ai-test-runs.md`](ai-test-runs.md) when it starts, rewrites it as results land (at most once a minute, at once on milestones such as a finished bundle), and marks it interrupted on SIGINT/SIGTERM or an early exit. The section holds counts, validity, cost and agreement only, never prompts or answers. This happens whether or not a decision has been made; that file is the raw evidence and this one holds the conclusions. Covered: `claude-effort-ladder.mjs run` and `capture-career`, `ai-task-replay.mjs`, `web-research-ab.mjs` and the live bundle harness `scripts/live-bundle-harness.mjs` (moved out of the git-ignored `tmp/` on 2026-11-10; the old path forwards to it) (`scripts/ai-test-journal.mjs`).
- `--out` must be durable. The tools refuse a session scratchpad, a Claude Code session temp folder or the OS temp folder; use `~/Library/Application Support/infinite-canvas/ai-test-runs/<name>` (or `tmp/claude-e2e/runs/<name>` for the live harness). `--ephemeral` skips both the check and the run log, for throwaway runs only. The live harness also copies its `--job` inputs into `<out>/inputs/`, so a run never depends on files in a scratchpad.
- When a run ends, copy its numbers into the call's row below with a link to its run-log section, even when the result is partial.
- A result no tool recorded itself (a blind-judge pass, a hand comparison, a number read off a transcript) goes in the run log at once with `node scripts/ai-test-journal.mjs record --tool <name> --task <call> --row "arm|n|valid|failed|cost|notes" [--fact Key=Value] [--note ...] [--out <durable dir>]`. Keep its inputs and scripts in that durable dir, never only in a session scratchpad.

- `scripts/claude-effort-ladder.mjs` (since 2026-11-15 `run` also takes DeepSeek arms: `flash:<off|low|medium|high>` and `pro:<...>`, sent through `offloadTextCall`, so one run ladders Claude and DeepSeek on the same records):
  - `capture-editorial` captures archived planner prompts.
  - `run` replays stored records at any `model:effort` list.
  - `capture-career` runs the real career compile through the app's own code. It has `--baseline-from` (replay stored answers for free), `--live-on-miss`, `--max-repairs`, `--only-records`, and `--profile-override task=model:effort` (one task at a different setting, run to convergence).
  - `summarize` prints per-setting validity and cost. Output dirs must be outside the repo.
- `scripts/interview-live-prepare-harness.mjs --research-profile model:effort` runs interview research at a given setting. Since 2026-11-09 the CLI runner returns `costUsd`/`usage`, so cost is recorded.
- `scripts/ai-task-replay.mjs`: offline replay of background tasks on stored board rows. `--configs` takes `claude` (the production baseline; `--claude-reps` sets the noise floor), `claude:<model>:<effort>` (added 2026-11-09), `flash:<reasoning>` and `pro:<reasoning>`, so one run can ladder Claude and DeepSeek together. Rows come from a canvas file with a scored board; the 2026-11-04 backup `canvas.json.before-content-pool-2026-11-04.bak` holds 569 scored rows. `scripts/ai-task-replay-score.mjs --out <dir>` scores validity, agreement with Claude rep 1 and cost.
- DeepSeek for application stages: replay archived prompts through `offloadTextCall` (the 2026-11-07 method in `docs/application-improvement-sessions.md`), or measure live with shadow mode (`INFINITE_CANVAS_SHADOW_OFFLOAD`, `scripts/ai-shadow-report.mjs`).
- Live: `scripts/interview-match-benchmark.mjs`, `scripts/interview-practice-benchmark.mjs`.
- Planted-defect audits: insert known defects into captured prompts, then count catches per setting, with the current setting as the reference.
- `scripts/web-research-ab.mjs --profile model:effort` runs the preference, compensation, role-family and location web-research tasks at any setting, with prompts rebuilt from a canvas file (2026-11-09). Use the same `--seed` and `--count` as the reference run, and compare the `native` arm per check. Do not use `ai-task-replay.mjs` for these tasks.
- `capture-stage --stage <name>` (in `claude-effort-ladder.mjs`) captures archived application-stage prompts for any stage from `claude-runs`. It covers fresh-session stages only. Stages that always resume a session (verify-correction, fit-correction) and stages that read page images (pick) cannot be replayed from logs.

**Recording for the next assessment (added 2026-11-09).** Every Claude call now leaves data that the next model release can be measured against without a new capture:

- `<userData>/ai-replay-samples/<task>/` holds the newest 24 prompts per task (owner-only). Each file includes the system text, the answer, the resolved model, effort, cost, usage, duration and the validator outcome. It covers background tasks, DeepSeek-routed ones included since 2026-11-20 (marked `"provider": "offload"`); the interview-stage folders date from before the 2026-11-18 move and are no longer written here. Turn the files into `claude-effort-ladder.mjs run` records by mapping `{id: <file name>, task, text, systemAppend}`. The ladder's default validator then applies the app's schema or planner checks; compare answers against the stored `answer`. This is the route for calls that had no replay tool: location consolidation, compensation assessment, gap review, repair, the career audits and the interview stages.
- `claude-task-usage.jsonl` gets one row per call with the resolved model id, so every result can name the version it ran on.
- `node scripts/ai-spend-report.mjs --user-data <userData> --runs-dir <canvas>/.local-ai/claude-runs` prints the annualized spend of every call, for the value-of-information rule (step 7). It annualizes over each log's whole span, not each call's own active days. A call used in bursts would otherwise look 4–6× too expensive. Application stages logged cost only from 2026-11-05 on, so their spend is the mean recorded cost × all logged calls, marked "estimated".

## New model release playbook (agreed 2026-11-10)

The app shows a red **Recalibration due** banner when a Claude call answers with a model id that differs from the calibrated set in `electron/ipc/aiModelCalibration.js` (`CALIBRATED_MODELS`). That set must match **Model versions tested** above. The banner stays until a recalibration is recorded here and the constant is updated to the new ids.

Assumption: within one family (Haiku, Sonnet, Opus), a newer version is at least as good as the one it replaces. So a proven setting still passes after the app moves to the new version, and the only open question is whether something cheaper now passes too. A full ladder is not needed again. Per release:

1. **Regression check (every affected call, one run).** Run the call's current setting on the new version against its stored production answers or run logs, and confirm it still passes: same validator rate, agreement within the call's noise floor, no new refusal or format failure. New versions can regress on a specific task (for example Sonnet safeguard refusals on `requirements`). Most calls replay offline for a few dollars. If it fails, treat the call as untested and ladder it in full.
2. **Re-check cost before stepping down.** "One step down" means the next *cheaper* setting for this call, measured, not assumed. Effort changes only the output side, so when input dominates the cost a lower effort saves nothing: `pick` (page images; Opus low $0.42 vs Opus high $0.46), `requirements` (Sonnet low cost the same as Sonnet high per job), `fit-correction` (resumes the writer session; output is a small share). Skip any step that cannot save money.
3. **Step down one rung, stop at the first rung that fails.** For non-live calls a rung fails when quality drops beyond the noise floor; for live interview calls, when the speed gain is insignificant or the quality floor is broken (the live-call rule in Policy). If a rung passes, keep stepping down.
4. **A new version of a cheaper family gets one probe from above.** When family X gets a new version, for every call currently set *above* X (a more expensive family), try X's strongest allowed setting (high, or xhigh where the call uses xhigh). Step down within X only if that passes. Reason: quality is ordered by price within a family, not always across families (preference research: Opus low confirmed 71 checks, the cheaper Sonnet medium 163), so a plain one-step-down from the more expensive family could stop before ever reaching the improved cheaper family.
5. **Live calls:** re-measure the current setting's p95 latency on the new version before stepping down. A new version is not reliably faster, especially in its first weeks.
6. **A new family** (a name other than Haiku, Sonnet, Opus): slot it into the ladder by price and test all of its efforts below max on every call it could serve. Fable and max effort stay excluded (Policy).
7. **Record and clear:** write each result with `scripts/ai-test-journal.mjs` (runs record themselves), update the call's row and **Model versions tested**, then update `CALIBRATED_MODELS` to the new ids, which clears the banner.

Every affected call gets the regression check and step-down; none is skipped for low spend (policy step 7). DeepSeek is out of scope for the banner: its alias does not expose a version (see DeepSeek results).

- **Untested**: never measured.

### 2026-11-21: re-test triage adopted

The rule that any changed prompt, schema or validator triggers a re-test is replaced by the triage in Policy (Re-test triage): each call has a baseline commit, a change is judged by its whole diff since that baseline, and only a change that can plausibly move the choice is tested (level 2 regression check or level 3 ladder; level 1 needs no test). Reason: tests are expensive, mostly in agent time rather than model calls, so a test runs only when a change can plausibly move the choice. This narrows policy step 7 ("every call is proven by a test") only for changed calls that were already tested; an untested call still needs its first test. Every row now carries a Baseline field, set from `git log --before=<test date>` on its prompt, schema, validator and tool files.
