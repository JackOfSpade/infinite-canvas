# Application improvement sessions

## Purpose and triggers

Improve application generation from real edits in batches, never from a single generation. More rules can lower quality; avoid rule creep.

Start a session when the private counter reaches 3, a bundle shows the due notice, the user asks to improve or review application generation, or the user announces a new ChatGPT model. The status also carries an early signal, `earlyDue` with `recurring`: one section of one document edited in four of the last eight accepted bundles since the last session, which is the shape a systematic defect takes. A bundle shows it as a suggestion; it is a reason to open a session early, not a rule by itself. Before each application bundle, the app also checks the edited bundles since the last session with one `application-edit-recurrence` handoff (the AI judges whether the same kind of change, not identical text, recurs across bundles). The result is cached by an input digest, so it costs a handoff only when the edit history changed, and the check is skipped while fewer than 3 edited bundles exist since the last session. While any pattern recurs in 3 or more bundles the app refuses to generate; the refusal clears only when a session ends with the counter reset. A failed check also refuses generation. The status prints the stored result as `generationGate` (pattern summaries and bundle counts only, no document text). At the start of *any* work on the application generator, check `application-improvement/state.json` in Electron's `userData` directory and mention if the counter is at least 3. The app keeps logging regardless of whether a session happens.

Three bundles trigger an evidence review, not a requirement to implement a solution. Extend the collection window when more data is needed to distinguish a recurring problem from isolated preferences and avoid overfitting solutions to a small sample. If there are too few usable edits or no sufficiently supported recurring pattern, record why the window is being extended and what additional evidence is needed. Keep the counter and existing evidence intact, leave the session due, and reassess as new bundles arrive. Do not force a guidance change to meet the three-bundle cadence. This extension does not bypass the recurrence generation gate described above.

The private store contains `state.json` (up to 100 full pairs and about six months of compact edit summaries), `archive/` (pairs from earlier model labels), and a separate `frozen-regression.json` (about 20 pairs selected by improvement sessions only). Each pair records the posting, generated and latest saved résumé and letter, timestamps, build (commit, dirty flag, build time), and model label. Each summary row records one changed block without its text: document, section, block kind, and operation (`added`, `removed`, `rewritten` with word counts, `moved`, `markup`, `regenerated`, or `not needed`). Summaries describe the edit; the session still assigns its category. A removed letter is erased from both versions and marked `not needed`. The saved version is treated as sent, except in a pair with `supersededAt`: a regeneration in the same folder replaced it. Its `supersededReason` (also on the `regenerated` summary row as `reason`) says what that means: `same-build` is a rejected generation, `rebuild` is a re-run of the posting under new app code and says nothing about the earlier text, and `unknown-build` predates build stamps. Only `same-build` pairs count as rejections. A pair may also carry `editNotesByDocument` (`resume` and `cover`) and `editNotesByDocumentAt`, the user’s reasons and save times from the separate document notes boxes. Historical `editNotes` / `editNotesAt` remain explicitly shared and unattributed; never infer their document. Keep all of these files out of Git.

`config/application-model.json` is the small tracked model label. Development sessions maintain it; the app has no control for it. On macOS, Electron's `userData` path is usually under `~/Library/Application Support/`; confirm the actual app path before running `node scripts/application-improvement-state.mjs status --data-root <absolute-userData-path>`.

## Career source changes

Successful career-data processing also records private evidence in `application-improvement/career-imports.json`. Both Job Search and Job Board drops use this same host-side log, after snapshot approval, clean-layer processing and final live-file checks. Cached imports are recorded too. A history-write failure fails the import visibly so a retry can use the approved cache and finish logging. A repeated request for the same run and snapshot is idempotent; a later distinct import remains a separate timestamped occurrence. The log retains ordered source names and byte hashes, snapshot IDs and compiler contracts, cache outcomes, and hashed canvas/module scope. It references the immutable `career-snapshot-store/career-snapshots/` evidence instead of duplicating source text. Keep both stores private and out of Git. History survives model transitions and counter resets.

The first observation in a scope is a baseline. A changed input fingerprint records a source change, which can mean content, selection, filename or order changes; it does not prove a factual correction. A different snapshot for identical input is a compiler change. An unchanged reimport is not a manual edit. These records show successfully **processed** sources, not proof the renderer adopted them: a result may subsequently be cancelled or superseded. No file watcher observes outside edits; they become observable only when imported and processed.

New improvement pairs carry the exact host-verified `careerSnapshotId` and `careerSourceFrozenAt` from their frozen generation job. The freeze time includes imports processed while an older-source generation was still running, before its eventual save or discard; the pair’s `generatedAt` alone is the logging time and cannot cover that interval. Do not substitute the globally latest import, a current module profile, or editable bundle metadata. The status command includes metadata-only history counts and dates. For a session, inspect the ledger with `node scripts/application-improvement-state.mjs career-history --data-root <absolute-userData-path>` and request before/after source evidence for each retained pair with `node scripts/application-improvement-state.mjs career-history --data-root <absolute-userData-path> --pair <pair-id>`. This read-only report loads the pair's exact frozen sources, compares them with later processed imports, and includes timestamps relative to generation and the latest save, scope uncertainty, and missing-evidence warnings. Its output contains private career text. Legacy pairs without a source pin remain explicitly uncertain; logging does not reconstruct earlier imports.

Before treating document edits as generator defects, compare the individual correction with the old and new source evidence. Classify it as **source-resolved** only when the later imported source actually supplies or corrects the relevant fact and is applicable to the career data used for future bundles; cite the pair, import and source evidence in the private session analysis. Verify adoption from the relevant module or a subsequent bundle's frozen source. A different hash, a later timestamp, or a matching filename alone is insufficient. Keep source-resolved edits as historical evidence, but exclude those individual corrections from proposed generator-rule changes and current-defect tallies. Still analyze unrelated wording, structure, length and evidence-choice edits in the same bundle. For offline replay, preserve the historical source pin and score source-resolved corrections separately, so an old-source mismatch does not become a generator failure. Validate a source correction with the revised source in a separately labelled run. Where provenance, adoption or retained evidence is incomplete, label the correction uncertain. Imports never automatically erase edits, reset the counter, clear the recurrence gate or weaken truth checks.

## New model

Update the label in `config/application-model.json` and rebuild the packaged app so it carries the new label. Let the app archive the previous full pairs and reset the counter on its next read or write. Verify the archived file and zero counter. Keep summaries and the frozen regression set. Make no code changes for the model transition itself. For application bundles the model and effort per stage are the runner's `CLAUDE_STAGE_PROFILES` table, so a model change edits that table and the label together.

## Improvement session

1. Load the pairs generated since the last session from the private store. The count can exceed the 100 full-pair retention limit; record the coverage actually available.
2. Classify every edit as truth error, evidence choice, wording, structure, length, letter structure, or user judgment call, and record source-resolved or uncertain status separately using the career source history above. Exclude removed letters from letter analysis. Read each pair's `editNotesByDocument` and any historical shared `editNotes` first; a stated reason decides the category over an inference from the diff. Inspect the following complementary records before assigning an explanation to a writing choice.

   Before each new writer candidate, a separate Opus call delivers a standalone annotated editorial outline. It proposes the thesis, body-paragraph points, the specific job needs they address, approved evidence IDs, short selection and omission notes, and factual qualifications. The exact frozen source and application brief are preserved. The outline is saved under the canvas's `.local-ai/editorial-plans/<jobId>/` before the writer starts and is bound to that handoff by the source and writer-prompt hashes. The writer receives the saved outline as a revisable proposal and identifies material departures in its final editorial summary. The roughly 300-word target is advisory; diagnostic formatting does not add a paragraph count or a new application acceptance gate. Malformed or unapproved-citation plans stop the run visibly instead of starting prose repair rounds. A plan is a proposal, not proof that its claims are true or that the writer followed it.

   The Agent SDK requests provider-generated thinking summaries through `thinking: { type: 'adaptive', display: 'summarized' }`, using the installed Claude Code executable. These summaries supply additional drafting context but do not represent an exhaustive or independently verified internal decision trace. Summary events are provisional until a successful provider result confirms the run; summaries received before a failure or cancellation remain explicitly provisional for diagnosis. Retention copies only readable summary prose and approved metadata. Signatures, redacted or encrypted thinking blocks, and raw provider streams are never retained.

   The writer's trailing `EDITORIAL SUMMARY` explains the finished application: thesis, each paragraph's point and target responsibility, selected evidence, résumé order, omissions, qualifications, revisions and material departures from the outline. It follows the completed documents and evidence appendix, then is removed from application text and archived with the evidence shortlist under `.local-ai/writer-shortlists/<jobId>/`; `decisionLogPresent` records whether it was supplied. Historical working-note replies remain readable. Missing final notes do not trigger a prose correction or change the truth gates. Compare the plan, native summary, final explanation, actual documents and source checks; none of the diagnostic records grants factual approval.

   Every Claude run appends correlated events under `.local-ai/claude-runs/<jobId>.jsonl`: start and the full prompt before the provider call, readable provider summaries, the full plain answer before submission, then the app's verdict, failure or cancellation. Events carry a run ID, prompt hash, stage, requested model/effort and session; provider errors retain their plain result and structured status metadata. Logging failures stop the run visibly. All three stores contain private candidate material and stay out of Git.
3. Keep only patterns that recur across several bundles. A one-off edit is evidence to inspect, not a new rule.
4. Propose at most about three changes. Prefer removing or replacing guidance over adding it, and keep the writer brief within a fixed size budget.
5. Test each candidate offline. Replay on the logged jobs and measure closeness to the latest saved versions. Also run a blind play-the-hand panel, truth recall, and the frozen regression set. Compare panel results only within this session using the same renderer. Ship only proven wins. The writer now runs locally through Claude Code, so a candidate brief can be replayed outside the live application with the runner's SDK options and stage profiles.
6. Append a dated Session log entry below with what changed, why, and before and after numbers.
7. Refresh the frozen set to about 20 representative pairs. Only the session changes this file. Reset the counter with `node scripts/application-improvement-state.mjs reset --data-root <absolute-userData-path>` after the entry and regression set are saved. The reset also clears the pre-generation gate, so generation resumes.

## Hard rules

- Truth checks are never weakened. A user-reported false claim is fixed immediately, outside this batch process.
- No candidate or posting facts enter tracked files, including tests and session notes.
- The oracle gate stays at zero ngram findings.
- Application bundles are written through the local Claude Code runner (`electron/ipc/claudeApplicationRunner.js`). The latest Opus plans and writes (xhigh effort) and judges (high). The latest Sonnet converts (medium) and makes the correction, trim and fact-check passes (high). The Agent SDK is the supported interface for readable provider summaries; it launches the installed Claude Code executable. Every other AI task stays on the ChatGPT bridge. A Claude failure, including a usage limit, stops the bundle loudly for the user to retry. It never waits or falls back to ChatGPT.
- Panel comparisons are valid only within one session with the same renderer.
