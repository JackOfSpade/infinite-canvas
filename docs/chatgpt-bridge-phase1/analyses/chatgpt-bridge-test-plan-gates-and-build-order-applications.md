# ChatGPT bridge: test plan, gates and build order (applications + push, always-on, app-supervised cloudflared)

Nothing of the real bridge exists yet: Phase 0 finished with GO and the lab is throwaway. Yes, one production plugin is still needed, but it can only be created once the app serves a live OAuth-protected /mcp, and only bridge-lab.lullascape.com exists today, so the plan ends with staging-plugin runs and then creation of the production plugin. This document specifies about 440 new registered tests in 13 files (no ports, no network, Node 22 safe), an out-of-band socket conformance script that uses the lab's MCP SDK client, a second local Electron smoke that enables the bridge for real, a manual packaged-app checklist, a staged synthetic ChatGPT run, a gated build order of stages B0 to B11 with parallel groups and worktree isolation, and the reversal procedure with an executable inert-when-disabled contract. Baselines were measured in a scratch copy outside the repo: 1486 tests in 49 groups, 0 failed, 18 s; lint clean; build:compile green. ## Design claims that no longer hold

- Design section 2 and 3 (Phase 1) and section 12 SOURCE-SCAN say Phase 1 changes ZERO lines of nonApiAi.js. Decision D4 puts the push seam in release one, so nonApiAi.js gets a bounded additive diff (verbatim hoist of :2393-2474 plus four small additions). The zero-diff gate now covers localAiApplication.js, NonApiAiDialog.jsx, useApplicationHandoffDock.js, applicationHandoffDock.js, JobCardNode.jsx and llm.js only; nonApiAi.js is guarded by a hoist-verification gate and the whole existing non-api-ai suite (75 tests today, not 76).
- Design section 5 MAIN.JS HUNKS says 'No startup hunk: the bridge never starts by itself'. Decision D5 (always available while the app is open) requires an auto-start on launch when enabled, so main.js gets a fourth additive hunk (a fire-and-forget start after createWindow at :1203, modelled on startApplicationSyncServer().catch at :1172). The refusal ladder (env kill, E2E, unpackaged, not enabled) lives in the controller, not in main.js.
- Design sections 3, 9 and T1 state the listener exists only while a session or pairing window is open, states off -> ready (NO listener) -> pairing -> session, idle 30 min / hard 2 h / per-request deadlines. Under D5 the listener and tunnel exist whenever the bridge is enabled, so every test that depends on those timers (design section 12 engine 'wall-clock deadlines enforced at request time with timers disabled', 'Force Quit leaves no listener') must be replaced by tests of the substitute controls (section 4 of the spec, A1-A10).
- Design section 8 and rejected alternative 2 say the app never spawns, supervises or holds credentials for cloudflared and that 'a crash or force-quit leaves nothing exposed'. D6 reverses this. A crash or SIGKILL of the app now can leave an orphaned cloudflared that keeps the hostname routed to the loopback port; the gate becomes 'no orphan after Force Quit and the next launch reaps it', plus tests for PATH-less binary resolution, binary trust, generated-config injection and env leakage.
- Design section 12 says no deterministic test binds a port or spawns a process. The port part still holds; the spawn part is stale (scripts/tests/job-api-probe.js:243 spawns node children with a fixture). Tunnel-supervisor tests may therefore use a small number of real child processes, generated at test time, provided they are killed in finally.
- Design section 5/12 assume oauth.js is pure (injected store) with store.js as the only fs user and that http/mcp/oauth/preflight/framing import only node:http, node:crypto and siblings. The reviewed lab oauth.js is a single file that imports fs, dns, https, net and path and contains the pid lock, atomic persistence and the client-metadata fetcher. To keep the source-scan rule the port must split it (core / store+lock / client-metadata fetcher) with a per-file import allowlist; the split must be a pure move so the 100-step suite stays the acceptance gate.
- Design section 8 item 2 says CIMD is deferred unless Phase 0 shows ChatGPT insists. Measured (RESULTS.md:151): ChatGPT chose the client-metadata document https://chatgpt.com/oauth/client.json by itself and never registered dynamically. Client-metadata support is required; dynamic registration and the static client are optional and unmeasured (the spec recommends dropping them from the port, which turns the DCR negative tests into a uniform-404 test).
- Design section 6 freezes the v1 tool text (INSTRUCTIONS in results, keep-going and retry text inside the tool descriptions). Measured: the v1 submit_handoff description triggered the 'Suspicious Instruction' banner; the frozen surface is v2s (design-tools.js SURFACES.v2s: submit_handoff reworded to documentation, get_handoff unchanged) and the behaviour text lives in the user's starter message. The pin is SHA-256 73c80b65…d5a2 and the whole wire tools/list (including execution and _meta.securitySchemes) must match a captured golden.
- Design section 9 and 8 numbers (access token 60 min, refresh idle 14 d / absolute 90 d, grace 60 s) differ from the lab defaults (accessTtlSec 300, refreshTtlSec 7 d ABSOLUTE only, graceMs 120 s in oauth.js resolveOptions). RESULTS.md:159 says tokens must live at least 1 hour or ChatGPT refreshes before every call. The tests must pin the final constants from one constants.js and must add an idle-expiry test only if idle expiry is actually implemented.
- Design section 12 says the OUT-OF-BAND script is scripts/handoff-bridge-selftest.mjs using the SDK client from the spike's node_modules or a devDependency. .mjs escapes the recommended lint rules, the spike directory is throwaway and its node_modules exists only after a local npm install, and a root devDependency would change package-lock.json and CI installs. The spec uses scripts/handoff-bridge-conformance.js with a separate scripts/handoff-bridge-conformance/package.json (pinned to the lab's SDK 1.30.1 and zod 4).
- Design section 12 SOURCE-SCAN says only sources/application.js imports localAiApplication.js and 'nothing in the directory imports nonApiAi.js until Phase 3'. With D4 only sources/push.js may import nonApiAi.js, and only the four seam names.
- Design section 3 Phase 1 exit ('Force Quit leaves no listener') and section 9 ('the app spawns nothing') are no longer sufficient: with D6 the exit criterion is no listener AND no orphan cloudflared after Force Quit, with the next launch reaping any leftover by pidfile plus process-table verification.
- Design section 5 says the bridge 'refuses to arm under INFINITE_CANVAS_E2E' and the existing e2e is unpackaged, so it can never exercise the enabled path; the enabled path has no automated Electron-level coverage in the design (manual only). The spec adds a second local smoke (scripts/electron-bridge-smoke.js) that uses the design's own INFINITE_CANVAS_HANDOFF_BRIDGE_DEV=1 gate with a fake tunnel binary, while the existing smoke remains the inert-in-E2E proof.

## 0. Are we done, and do we need a production plugin?

No, and yes.
- Not done: Phase 0 (measurement) ended in GO. The real bridge, its tests and its supervisor do not exist; the lab in `scripts/chatgpt-handoff-spike/` is throwaway and is a source to port from, not to import.

Creating a plugin makes ChatGPT probe the URL and run the OAuth discovery immediately (RESULTS.md:25, :150), so the app must already serve a live OAuth-protected `/mcp`. A fresh plugin also has a warm-up of about 20 to 25 minutes in which writes were blocked (RESULTS.md:43-50).

- Plan: build and test everything against a fake tunnel, run the staged synthetic ChatGPT stages on a STAGING plugin at the lab hostname, then create the production plugin (S7 onward), wait out its warm-up, repeat the short drills, and only then let Jack run one real job. The four lab plugins A to D in ChatGPT should be deleted (RESULTS.md:191).

## 3. Assumed controller API and the always-on controls the tests target

The tests are written against these names. If the architecture spec renames something, search and replace; the assertion shapes do not change.

Controller (`electron/ipc/handoffBridge/index.js`): factory `createHandoffBridge(ports)` returning `{enable, disable, start({reason}), stop({reason}), status, releaseJobs, holdJob, resumeJob, openPairing, disconnect, trip(reason), handleRequest, dispose}`; module wrappers `registerHandoffBridgeHandlers()`, `startHandoffBridge({reason})`, `stopHandoffBridge()`, `getHandoffBridgeStatus()`. States: `off, starting, ready, degraded, tripped, paused, stopping`. Refusal reasons (this precedence, first match wins): `env_disabled, e2e, unpackaged, not_enabled, no_hostname, no_binary, binary_untrusted, no_credentials, config_invalid, port_in_use, tunnel_failed, state_unreadable`. `e2e` is evaluated before `unpackaged` so the existing smoke (which is also unpackaged) proves the intended guard.

Substitutes for the removed session timers (proposal; the security analysis owns the final list). Each has a named test in `handoff-bridge-controls.js`:

| Id | Control | Test shape |
|---|---|---|
| A1 | Release gate: the listener is always up but nothing is served until Jack releases specific jobs through a main-owned native confirmation naming jobs, canvases and destination; a release ends when the job saves, is discarded or is held | zero released jobs: every authenticated call returns a nothing-released status and the adapter spies record 0 calls; the stub's default confirm answer releases nothing |
| A2 | Credential lifetimes: access token at least 3600 s (measured need), absolute refresh lifetime, idle refresh lifetime only if implemented | fake clock advanced by days; link dies at the absolute limit; tokens keep working just before it |
| A3 | Trip (auto-disable) on credential-attack evidence: refresh reuse outside grace, wrong chat key with a valid token, repeated wrong client secret; state `tripped` closes the listener and kills the tunnel; only Jack re-enables | trip closes both; anonymous noise of any volume never trips (a stranger must not hold a kill switch, design line 311) |
| A4 | Source class: requests carry Cloudflare headers when they came through the tunnel; direct loopback callers are classed apart and audited | Host pin, header parsing (IPv4, IPv6, spoofed values), class counted in the audit line |
| A5 | Bounded permanent listener: caps on transactions, codes, clients, families, rate-bucket keys (LRU), audit size and rotation | flood tests assert map sizes stay under the caps |

## Risks

- Node version gap: local Node is 26.4 and CI is Node 22; the portless HTTP harness and esbuild mount prototypes were only verified on 26.4. Run act at B2, B5a and B8 (not only at push time) and avoid any API newer than Node 22; confirm the Electron 42.9 embedded Node version (not measured).
- The in-process fake HTTP driver can drift from real Node HTTP behaviour (header casing, chunking, socket events). Mitigation: one driver-neutral request table run through both the fake exchange and the real-socket driver, results must be identical; explicit Content-Length everywhere; req.complete=true pitfall documented.
- Porting the 1,856-line reviewed oauth.js while splitting it can silently lose the review. Mitigation: pure moves verified with git diff --color-moved, the 100 steps as one-to-one acceptance, the oracle run against the lab file until the lab is retired, and a fresh /security-review on the split code.
- Pushing any stage branch triggers CI and the auto-merge workflow lands it on main. Keep branches local, merge fast-forward, push main only on Jack's word (the pre-push act gate then runs for several minutes).
- nonApiAi.js is a 2,581-line heavily source-pinned file (75 tests plus pins in job-diagnostics and others). The seam must ship as a verbatim-hoist commit first; a reordering or reformatting of the hoisted body can break raw-substring pins even when behaviour is identical.
- Always-on plus app-supervised cloudflared widens exposure: a crash or Force Quit can orphan a connector that keeps the hostname routed to the loopback port; two connectors for one tunnel would split ChatGPT's traffic between two Macs. The reaper, the single-connector check, unpackaged-build refusal for the production hostname and the OOB orphan drill are the containment; none of it is proven until B3 and B9.
- The Host header seen through real Cloudflare was never measured (design E9); the generated ingress sets httpHostHeader to make the pin deterministic, but this must be checked in M4 before relying on it.
- The staging-plugin and production-plugin plan assumes ChatGPT treats an identical frozen tools/list as unchanged; any byte drift in the wire JSON (execution, _meta, key order, $schema) forces a Refresh and may reset the warm-up. The golden test is the only protection.
- ChatGPT-side variance is not testable offline: one intermittent safety block after a reconnect was observed in 23 lab chats, warm-up reset by edits (E3), renderer throttling (E5), sleep (E10) and a real 2 h outage were never measured; the staged run can only sample them.
- A new test-only path (the DEV flag used by the bridge smoke) exists in production code; it must stay unpackaged-only and must refuse the production hostname, and the smoke must never set the E2E flags (which have to keep proving inertness).
- A single test process runs all 1,900+ tests: an unhandled rejection, a leaked timer or a leaked child from a bridge test fails or hangs the whole runner without attribution. Mitigation: withLeakCheck, tracked child helper with exit hook, unref timers, injected scheduler.
- The current unit suite has no coverage of component render bodies; the new esbuild+jsdom mount helper is a new pattern (prototype verified once) and could be flaky under act warnings if unmount is not wrapped.
- cloudflared upgrades (Homebrew) can change flags or log text; auto-update is disabled and readiness uses the pidfile rather than log parsing, but a flag rename would surface only at runtime (argv snapshot passes with the fake). M4 with the real binary is the guard.
- Estimates (about 29 engineer-days, +25 to +40 s of unit time) are unmeasured; the OAuth port and the seam are the largest uncertainties.
