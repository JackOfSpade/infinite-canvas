# ChatGPT bridge, Phase 1: staged build plan

Generated 2026-09-26 by a planning workflow (7 analysts, a synthesizer, 2 critics) from Jack's decisions D4 (applications plus scoring/push), D5 (always armed) and D6 (app-spawned cloudflared) and the Phase 0 measurements. **Status: NOT approved to build.** Both critics require edits first (see `critiques.md`); those edits must be folded into `addendum.md` and this plan before stage B0 starts.

## Effort

About 36 engineer-days of agent work (B0 1.5, B1 2.5, B2 4, B3 4.5, B4 4, B5a 1.5, B5b 2.5, B6 5, B7 4.5, B8 3, B9 0.5, B10 2), unmeasured. With five concurrent worktrees in the first wave (B1 to B5a) and B6 and B7 in parallel, the critical path is roughly 1.5 (B0) + 4.5 (slowest of P1: tunnel or OAuth) + 2.5 (B5b) + 5 (B6) + 3 (B8) = 16.5 working days, plus B9/B10 (about 2.5) = about 19 working days, and I would plan 22 working days (4 to 5 calendar weeks) for uncertainty in the OAuth port, the seam and the tunnel's real-cloudflared behaviour. Not agent time: about half a day of Jack setup (Cloudflare tunnel and route, plugin creation), 3 to 4 hours per staged ChatGPT session block, three 30-minute plugin warm-up waits, and one overnight soak. Nothing before B6 changes app behaviour; the bridge is off by default and inert under E2E until Jack enables it.

## Residual risks Jack accepts

- Cloudflare and OpenAI read every prompt and answer in plaintext; every served application prompt carries the career corpus, so per-job release limits which listings and drafts are exposed, not the corpus.
- The OAuth link is not account-bound: ChatGPT's client document has one redirect for every user, so a stranger's plugin looks identical to yours. Only the pairing code, the same-network check and the 10-minute window stand between a stranger and a link; screen sharing or shoulder surfing during pairing defeats them.
- A refresh token is a bearer credential (ChatGPT is a public client); theft inside the 120 s grace window is invisible; until gate G1 shows ChatGPT signs assertions there is no client authentication, and source-prefix enforcement stays alert-only until 14 days of data (gate G3).
- Prompt injection is bounded only by model behaviour: 0 of 9 canaries allows a true failure rate up to about 28% at 95% confidence, one model and effort, browsing state never recorded; another tool in the same chat (memory, browsing, other apps) is an exfiltration path the app cannot police.
- The public hostname is fingerprintable and floodable whenever the app is open with the bridge on. The app sheds load but deliberately has no listener-closing breaker, so a flood can deny legitimate calls; a rogue second connector or hijacked DNS record is invisible from the origin.
- Always-armed with the optional timers OFF (literal D5): a forgotten release or chat key stays valid until you act, and idle never pauses. The data-based controls (release set, 2-job chat cap, byte budget, anomaly pause, Pause/Revoke, Tray visibility) are the only bound.
- The app-spawned cloudflared can be orphaned by a crash or Force Quit for about 2 seconds (the /bin/sh watchdog) and for longer only if the shell wrapper itself dies; the next launch reaps it. The Homebrew binary is ad-hoc signed with no Team ID, so authenticity rests on a trust-on-first-use SHA-256 pin that a same-user attacker can rewrite; every brew upgrade needs a re-approval.
- Hand-rolled OAuth and MCP code in the privileged Electron main process is the only parser of untrusted bytes; mitigations are the ported 100-step suite, the import allow-lists, the negative battery and a /security-review before any real data crosses it.
- Renderer-driven job completion: a bridge chat can only drain to paste-completed; import, PDF fit and measured-fit reopen need an open canvas window. With no window a job stalls as host_silent after 10 minutes and macOS keeps the app alive with no window.
- Chat context is the binding limit for scoring: about 60 KB prompt plus 40 KB answer per handoff means a chat may take only about 4 handoffs before New chat, and one serial chat is roughly 3 to 4 times slower in wall clock than ten manual chats (it saves your attention, not time). 35 to 65 KB tool-call arguments are unmeasured (largest ever sent 25.7 KB) and a chat can end one scoring phase early because phase changes are renderer-driven.
- ChatGPT-side blocks never reach the server (one after a reconnect was seen); a new plugin has an unexplained early write-block window of about 20 minutes; whether editing tool text or the URL resets the warm-up, sleep, renderer throttling and a real 2-hour outage are unmeasured.
- get_handoff keeps readOnlyHint:true although it can write in recovery paths (localAiApplication.js:3699-3711); the Generation Log crash window (D7) remains until you schedule that separate app change; bug reports cannot tell bridge rounds from pastes without the optional D10 telemetry.
- Several small deltas from the linked lab configuration are unmeasured until acceptance: AS auth methods reduced to ['none'], Origin allow-list, the composite starter used for scoring prompts, /ready and edge status-code mappings for cloudflared, the Host header through Cloudflare, and the watchdog wrapper behaviour on macOS.

## Contradictions between the analysts and how they were resolved

- Release model under D5: the UI analyst had renderer-published jobs flowing continuously with no per-job confirm; the application analyst and security analyst required a main-owned native confirm per release and warned the renderer has no CSP. Decision: persisted release set with a native confirm per batch; the renderer only publishes CANDIDATES (with a change signature) and a sanitized label crosses IPC only on the release call; optional autoRelease (own confirm, default off) gives the hands-off experience.
- Timers under D5: the security analyst proposed default release lapse 24 h, chat-key max age 24 h and idle pause 180 min; the application analyst and the literal decision say no timers. Decision: the controls exist but default to 0 (off), each raising change needs a native confirm, and data/count-based controls (release set, 2-job cap, byte budget, anomaly pause, Pause/Revoke, visibility) carry the load. Recommended values are documented for Jack to switch on.
- GET hold and wait cap: 10 s x 8 (design, push analyst) vs 20 s x 10 (application analyst).
