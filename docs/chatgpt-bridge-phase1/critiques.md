## Hostile security review of the revised ChatGPT bridge (D4 push seam, D5 always armed, D6 app-spawned cloudflared, in-app OAuth). Analysis only: nothing written in the repo, no network, no servers. Scratch evidence is under /private/tmp/claude-501/-Users-jack-Desktop-My-Apps-infinite-canvas/c5a34b5f-3705-4274-beaa-9079f1f21b5b/scratchpad/sec-review/ (unix.yml, cf-strings.txt).

**Verdict.** NOT READY TO BUILD AS WRITTEN. The architecture holds and nothing here reopens D4, D5 or D6, but several controls do not stop what the addendum says they stop, and D5 is only met in letter. The addendum's line anchors all matched the code I opened (main.js:1289/1343-1365/1385/1399-1400, nonApiAi.js:2199/2386-2474, localAiApplication.js:58/825/3863/3959/4897/5250/8754, logger.js:21). Result per threat (STOPS / PARTLY / NO):

1. Token and pairing weaknesses: PARTLY. The pairing gate is sound (50-bit code shown only in a native sheet, one live code, 5 tries per request and 15 per window; the lab consumePairing at oauth.js:984-995 is constant time). Weak points: the chat key is 50 bits, SHA-256 at rest, persisted across restarts (epoch.json) with no expiry; the refresh token is a pure bearer even though ChatGPT's own client document (selftest-oauth.js:804) declares token_endpoint_auth_method private_key_jwt, RS256, jwks_uri https://chatgpt.com/oauth/jwks.json; an anonymous GET /oauth/authorize can raise an in-app hint every 60 s; the network gate rests on a header any loopback client can forge; the link is not account bound (accepted).
2. SSRF through the client-metadata fetch: STOPS for CIMD (exact client_id pin before any fetch, https only, no redirects, 16 KiB cap, DNS-guarded lookup at oauth.js:415-431 and 433-490, window and network gate first). Not covered: the app's own probes to a configured hostname, the future JWKS fetch, and DCR, which is still open inside the window.
3. Request smuggling through the tunnel: MOSTLY STOPS (Cloudflare, cloudflared and Node's strict llhttp parser in series; exact route match; explicit Content-Length). Gaps: early rejections leave unread bodies on kept-alive sockets (only 404 sets Connection: close), Node auto-answers Expect: 100-continue (checkContinue listener count is 0, verified), unauthenticated body dumping is uncapped.
4. Local-process and browser access to 127.0.0.1: NO. Fixed port 43193; Host 127.0.0.1:<port> and localhost:<port> accepted on every route (only Origin guards the mutating ones, and GET /oauth/authorize is exempt); Cf-Connecting-Ip is forgeable by any client that can reach the socket, and 'trusted only because the TCP peer is loopback' is vacuous because cloudflared is loopback too. cloudflared 2026.9.3 accepts unix: origins (verified offline with `tunnel --config ... ingress validate`), so this class can be removed.
5. Injection into cloudflared arguments or config: STOPS for remotely or renderer supplied values (validators, argv array with shell:false, JSON-quoted credentials path, exact-output dry run, env whitelist which also blocks DYLD_* and TUNNEL_*; every flag the plan names exists in this binary's help). Remaining: hash-then-exec TOCTOU, loopback metrics/pprof, the management service, same-UID rewrite of pin and config.
6. Log and bug-report leaks: PARTLY. The enumerated logger is right (V8 JSON.parse errors do quote body text, verified). But anonymous events would enter the 200-entry app ring (logger.js:21, read by bugReport.js:2091) and the audit ledger keeps only 2 MiB.
7. Cross-job answer routing: STOPS for application jobs (random 24-char codes routed by index, envelope jobId and stage preflight, tombstones) and for push (routed by the requestId served to that chat). The persisted-epoch design adds an envelope-routing fallback (9.7) that should go away with edit 1.
8. Flood denial of service: NO as written. Pre-auth semaphores and the aggregate bucket are shared with authenticated calls, buckets are keyed by full IPv6 addresses with a 512-key LRU, and maxConnections 64 sits under cloudflared's keep-alive pool.
9. Hostile listing steering tool calls: PARTLY. Server-side, out-of-order calls reduce to junk, wrong-code or duplicate submits, all bounded by preflight, caps and pause, and nothing outside the released set is reachable. Residual is model behaviour: the canary is 0 of 9 (upper bound about 28%) for one injection style, and validationErrors echo model text in a channel the tool text tells the model to obey.
10. App left running for days: NO as written. The epoch, key and release set survive restarts, key and release never expire, and detection is silenced by the attacker's own calls. Edits 1, 13, 16 and 20 fix this without a timer.
11. Crash or Force Quit leaving the tunnel connected: PARTLY. Watchdog plus reaper is right, but the watchdog has no KILL escalation, cloudflared's default grace is 30 s, and quit does not quiesce serving until the very end.

   - Problem: [MED] The forensic window is 2 MiB of per-call lines: a get poller at the allowed 1 call/s (burst 60) overwrites it in about 3 h. Under D5 nobody is watching for days. The nudge fires on the absence of authenticated calls, which is exactly what an attacker's calls suppress, and nothing alerts on a serve that happens long after Jack last acted.
   - Fix: Two ledgers: security.jsonl (link, refresh, revoke, pause, resume, pairing, release, new-chat, epoch close; 5 MiB x 4, never rotated by call volume) and a compact serve ledger of served, accepted and rejected transitions only (no waiting, empty or paused gets). Replace the nudge with: 'bridge on N h with no New chat, Continue or release by you', plus a generic notification whenever a served result occurs more than 12 h after the last human epoch action.

### Concerns

- Cloudflare and OpenAI are the trust root: Cloudflare terminates TLS and sees bearer, chat key, prompts and answers; the management service can stream connector logs to whoever holds the Cloudflare account (unverified whether debug-level headers can be pulled). Origin-side controls cannot fix this; only account hardening, source enforcement (edit 13) and private_key_jwt (edit 4) narrow replay.
- The link is not account bound: ChatGPT's client identity and single redirect are identical for every user (selftest-oauth.js:804), so any ChatGPT user who learns the hostname can start a transaction. Only the window, the code, the network gate and a single grant stand in the way; pairing-window fatigue is a real social-engineering surface once Reconnect becomes a routine event.
- Prompt-injection evidence is thin: 0 of 9 hostile chats bounds the failure rate only to about 28% at 95% confidence, one model and effort, one injection style (echo a marker, open a URL), browsing state unrecorded. It says nothing about subtle steering of scoring or résumé content, which validators only partly catch. Another tool in the same chat (memory, browsing, apps) is an exfiltration path the app cannot police.
- D5 as decided means a stolen credential has no clock; after edits 1, 4, 13 and 20 the remaining bounds are release set, epoch close on drain, source enforcement and credential lifetimes. Jack should decide knowingly whether idle-pause (default off) should stay off.
- Renderer trust: no CSP in index.html (grep), preload only in the main frame; native confirms are the only boundary and every exposure-raising IPC must be confirmed in main. autoRelease weakens that unless restricted to main-observed queueLocalApplication jobs (edit 6).
- Reuse detection is availability-hostile by design: any old refresh token replayed after 120 s revokes the link, retires the epoch and pauses serving; recovery needs a pairing window at the Mac.
- Same-UID attackers are out of scope but worth naming: the pin, tunnel config, oauth-state.json and lanes.json are all writable by the same user, so the pin is change detection, not protection.
- Hand-rolled OAuth and MCP in the privileged main process remains the only parser of untrusted bytes; process.on('uncaughtException') swallows (main.js:215-222), so a logic bug degrades silently instead of crashing. utilityProcess isolation would fix event-loop coupling only.
- The design's Phase 0 caveats remain: warm-up reset by URL or tool edits, renderer throttling, sleep and wake, and one ChatGPT-side block after a reconnect are unmeasured; a hostname change (edit 19) resets warm-up, another reason to decide it before S7.
- Unverified from my side (read-only, offline): whether Cloudflare's free plan allows the suggested custom rules and rate limit, cloudflared's actual default keepAliveConnections (I recalled 100; keys are present), whether a copied ad-hoc binary runs under the app's local signing identity, and whether Cloudflare overwrites a client-sent Cf-Connecting-Ip in every case. Each is a measurement item, not a claim.
- Second-order integrity: even with every control above, a poisoned but validator-passing answer from a steered model is written into Jack's application files and scoring; the plan's mitigation is Jack's review of the finished output, which unattended draining reduces.
