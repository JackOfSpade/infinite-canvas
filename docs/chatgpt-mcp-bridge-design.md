# ChatGPT MCP handoff bridge: design

**Status:** DESIGN ONLY. Nothing here is built. · **Date:** 2026-09-26 · **Branch:** `design/chatgpt-mcp-bridge` (from `spike/chatgpt-mcp-handoff`)
**Inputs:** the feasibility spike (`scripts/chatgpt-handoff-spike/RESULTS.md`, verdict GO on fake data) and a 15-agent design workflow: 5 readers (transport, application flow, renderer dock, Electron host, external URL/auth options), 3 independently framed designs, 6 adversarial critiques (security/privacy and integration/reliability, per design), 1 synthesis. The synthesis text below is that workflow's output, with the front matter and the "Verification notes" section added afterwards by hand.

## 1. Conclusion (read this first)

**Proceed, but gated.** The mechanism is proven: ordinary ChatGPT Chat drove the whole handoff loop through a custom MCP plugin with no copy/paste (spike, 3 runs). The design below is sound on paper and cannot regress the copy/paste path, which stays the permanent fallback. But two things the spike did not test can still sink the project, so **the next step is a measurement phase (Phase 0), not the build**:

1. **OAuth on Jack's Pro personal account.** ChatGPT cannot send a static header or key, so authenticated access means a real OAuth 2.1 server. The spike used "No auth". Whether the create-app dialog's OAuth flow works on this account, carries into the desktop app's Chat, and survives token expiry is unmeasured.
2. **Real-shaped payloads.** The spike's fake data had employer names, percentages and `$` amounts (all passed) but **no emails, phone numbers, URLs, real names or addresses**, at 14-15 KB with 6-character codes. Real handoffs carry all of those at 18-65 KB with 24-character mixed-case codes. ChatGPT's safety layer has blocked payloads for opaque reasons before.

**Recommended design in one paragraph.** An *armed-session* bridge inside Electron's main process: a hand-rolled MCP server (no new dependencies) with exactly two frozen tools, `get_handoff` and `submit_handoff`, that only listens while Jack has started a session. ChatGPT reaches it through a Cloudflare named tunnel that Jack runs himself outside the app. ChatGPT authenticates with an in-app OAuth 2.1 authorization server (opaque hashed tokens, PKCE S256, consent by a one-time pairing code typed from the Mac's own screen) plus a per-chat key. The tools drive the *existing* `getLocalApplicationHandoff` / `submitLocalApplicationHandoff`, so every answer passes exactly the parser, envelope check, batteries, correction prompts and durable commit a manual paste does. Phase 1 changes **zero lines** of `nonApiAi.js`, `localAiApplication.js` and the dock, is off by default, and is reversible by deleting one directory and three small hunks.

**What it saves.** For application bundles, 6-10 round trips of about 4 manual actions each become one kickoff message per ChatGPT chat plus a Start click. Scoring/push runs (`requestNonApiAi`) are deliberately deferred: generation time dominates them, so the saving would be copy/paste actions rather than wall-clock, and attachment/grounded tasks can never be bridged.

**Effort (estimates, unmeasured).** Phase 0: 2-3 working days plus calendar waits (no app code). Phase 1: 10-13 working days. Domain about 10-15 USD per year (unverified) and about 30 minutes of one-time setup.

**Suggested split of Phase 0** (because the OAuth and hostname tests need a stable hostname but the payload tests do not):
- **0a, needs no domain, no money, no auth:** extend the spike with the real prompt wording, realistic synthetic PII, 40-60 KB results and 20-30 KB answers, over the existing quick tunnel; 3 fresh-chat runs. Answers whether real-shaped content gets blocked.
- **0b, needs the stable hostname:** OAuth linking and refresh, web-created plugin used from the desktop app, the warm-up reset tests, Cloudflare specifics, held-call and throttling measurements.

## 2. Recommended design

ARMED-SESSION CHATGPT HANDOFF BRIDGE, application bundles first. Repo root: /Users/jack/Desktop/My Apps/infinite-canvas.

WHAT IT IS. A zero-new-dependency MCP server inside Electron main (new directory electron/ipc/handoffBridge/) that exists only while Jack has started a session. ChatGPT reaches it through a Cloudflare named tunnel that Jack runs himself (cloudflared outside the app). ChatGPT authenticates with an in-app OAuth 2.1 authorization server (opaque hashed tokens, PKCE S256, a one-time pairing code Jack types from the Mac's own screen) plus a per-chat session key passed as a tool argument. Two frozen tools, get_handoff and submit_handoff, drive the EXISTING pull functions getLocalApplicationHandoff and submitLocalApplicationHandoff (electron/ipc/localAiApplication.js:3863, 3959), so every answer meets the same parser, envelope echo check, batteries, correction prompts, rejection-streak escalation and durable commit as a manual paste. Text-only scoring/push handoffs (requestNonApiAi) are Phase 3, optional, via a behavior-preserving hoist of the submit handler body (electron/ipc/nonApiAi.js:2393-2474).

WHAT PHASE 1 TOUCHES IN EXISTING CODE. electron/main.js (3 additive hunks), electron/preload.js (additive lines), src/App.jsx (one import, one element after <NonApiAiDialog />), src/components/SettingsPanel.jsx (one section), scripts/test-runner.js (registrations). It changes ZERO lines of nonApiAi.js, localAiApplication.js, NonApiAiDialog.jsx, useApplicationHandoffDock.js, applicationHandoffDock.js, JobCardNode.jsx and llm.js (checked by git diff --stat in review). The copy/paste dock therefore behaves exactly as today in every state: bridge off, broken, blocked or stalled. Inference stays in ordinary ChatGPT Chat; the bridge only hands out prompts and accepts answers and calls no model API.

SETTLED BY ME (evidence-backed; not Jack's call):
1. Hand-rolled JSON-RPC subset (initialize, ping, notifications/*, tools/list, tools/call). No MCP SDK, zod, ajv or express in the app; the spike's SDK client is used only in an out-of-band conformance script. Removes lockfile, rolldown-interop and packaged-asar risk (nothing gates the packaged runtime: scripts/electron-smoke.js:242 launches unpackaged).
2. No relay, no app-spawned tunnel, no safeStorage, no utilityProcess in Phase 1 (reasons in section 13).
3. Exactly two tools, frozen at the end of Phase 0; anything that must evolve lives in tool results.
4. One active ChatGPT chat per session, depth-first per job. 'New chat' rotates the chat key so a stale or duplicate chat is fenced off. No ticket alias: routing is by the app's own handoff code.
5. A bridge-side pre-check that never touches app state for junk, wrong-job or wrong-stage submissions; fixed-string error mapping; no scraped strings in any bridge-authored field.
6. The paste box is never disabled (hard rule c); the human always wins; a non-bridge advance auto-holds that job.
7. Consent is one main-owned native confirmation at Start that names the jobs, canvases and destination host; the job set is fixed for that session.
8. Bridge state is hashed at rest under <userData>/handoff-bridge/, outside electron-store config.json and outside node data (no versioned migration needed).
9. Default limits: session idle 30 min (10 after queue_empty), hard 2 h wall-clock deadline checked on every request, access token 60 min, refresh idle 14 d and absolute 90 d with 60 s predecessor grace, get hold 10 s (tuned in Phase 0), session budget provisional 500 KB soft / 900 KB hard, per-job rejection cap 6.
10. Application bundles first; push behind a task allowlist, never attachments, grounded, marketplace or price tasks.

NOT KNOWABLE FROM THE REPO (gates, not assumptions): whether OAuth linking works on a Pro personal account and carries into the desktop app; the block rate with real PII at 30-65 KB; whether the real paste-worded prompts still make the model call submit_handoff; whether URL or tool edits reset the ~12-20 min warm-up; held-call tolerance; context growth; renderer throttling when ChatGPT is frontmost. Phase 0 (no app code, synthetic data only) measures each and stops the project if the gates fail.

## 4. Decisions for Jack

### D1. Accept Cloudflare (a new reader of plaintext prompts, answers and career data in transit) as the public path?

- **Options:** Yes, Cloudflare named tunnel on a domain you own (proven edge with ChatGPT in the spike; Cloudflare can technically read traffic) | No: Tailscale Funnel (TLS terminates on your Mac so no new reader; free ts.net name; needs Tailscale account plus MagicDNS/HTTPS/funnel ACL setup; ChatGPT compatibility has only third-party evidence, so add a one-hour Phase 0 pre-flight) | No: stay on copy/paste
- **Recommendation:** Cloudflare named tunnel, with the tradeoff written into the runbook and the Settings copy. OpenAI already receives the same plaintext; the added reader is Cloudflare on your own account. If that still feels wrong, run the Tailscale pre-flight and switch.
- **Why it is yours:** It decides who can read your career data in transit, which is a privacy risk acceptance, not an engineering fact.

### D2. Money and accounts: buy or reuse a domain, create a Cloudflare account/zone (nameserver move), create the tunnel and the ChatGPT plugin, and secure them.

- **Options:** Buy a dedicated cheap domain on a dedicated Cloudflare account with hardware-key 2FA and a registrar transfer lock | Reuse a domain you already own | Skip the bridge
- **Recommendation:** Dedicated domain and account: the hostname and the tunnel credential are effectively the bridge's identity, and a registrar or Cloudflare compromise means a rogue connector can read prompts. Expect about 10-15 USD per year (unverified), about 30 minutes of setup, and a 25-minute warm-up after creating the plugin. I cannot create accounts or spend money for you.
- **Why it is yours:** It spends your money, needs your accounts and payment details, and ties your identity to registrar and Cloudflare records.

### D3. If Phase 0 shows OAuth cannot be made to work on your account, what is the fallback?

- **Options:** Stop and stay on copy/paste (recommended) | Mixed auth mode if it passes Phase 0 | Capability URL plus the per-chat key plus armed sessions only: a deliberate downgrade from what RESULTS.md:55 said real handoffs need
- **Recommendation:** Stop, or use Mixed mode only if it passes. Do not send real career data behind a secret-in-URL scheme unless you accept in writing that anyone who learns the URL and key during a live session can read the current prompt and submit an answer.
- **Why it is yours:** It is an explicit acceptance of a weaker security posture for your own data.

### D4. Scope of the first release.

- **Options:** Application bundles only (Phase 1); push later or never | Applications plus scoring/push from the start | Everything, including attachment and grounded tasks (not possible over MCP)
- **Recommendation:** Applications only. It is where the 6-10 round trips per job hurt, it needs no edit to nonApiAi.js or localAiApplication.js, and it is durable across restarts. Push runs are dominated by ChatGPT generation time, not by copy/paste, and attachment tasks can never be bridged.
- **Why it is yours:** It is a product-value call about where your time goes.

### D5. Approve or change the default limits: session idle 30 min, hard 2 h wall-clock cap, one active chat, about 2 jobs per chat before 'start a new chat', per-job rejection cap 6, stall notice at 4 min, get hold 10 s.

- **Options:** Approve as listed | Shorter (tighter exposure, more clicks) | Longer or always-armed while the app is open (fewer clicks, larger exposure window)
- **Recommendation:** Approve as listed; they are conservative first guesses (slowest observed legitimate step ~1m50) held as constants in one file and re-tuned from Phase 0 and Phase 1 measurements. Do not choose always-armed.
- **Why it is yours:** The exposure window versus convenience tradeoff is a risk tolerance.

### D6. Who runs the tunnel process?

- **Options:** You, as a launchd agent outside the app (recommended) | The app spawns and supervises cloudflared (orphans after a crash, PATH lookup under a GUI launch, a binary to trust or sign, generated config that could be injected) | Optional Phase 2: the app only starts and stops your launchd agent with launchctl while a session is live
- **Recommendation:** You run it. The app then never holds a tunnel secret, spawns nothing, and a crash leaves nothing exposed. Revisit the launchctl refinement in Phase 2 if you dislike a standing connector.
- **Why it is yours:** It decides where a long-lived third-party credential lives on your Mac and how much you are willing to operate by hand.

### D7. Fix the pre-existing crash window in the application accept path (Generation Log appended before the manifest write; a different resubmission after a crash between them throws and wedges the stage).

- **Options:** Separate small change to localAiApplication.js: recover when manifest.logCount is behind the log tail | Rely on the bridge's identical-bytes resubmit rule | Leave it
- **Recommendation:** Separate small change before or during Phase 2. It is equally reachable by a human paste and very rare; it is not a Phase 1 gate. It touches a heavily source-pinned file, which is why it is yours to schedule.
- **Why it is yours:** It modifies core app code outside the bridge and its test pins.

### D8. ChatGPT-side hygiene you must set up yourself: a dedicated Project or chat for handoffs with memory, web browsing and other connected apps off, data controls set as you want, and chats deleted afterward.

- **Options:** Do it (recommended) | Skip it and accept that other tools in the same chat are an exfiltration path the app cannot police
- **Recommendation:** Do it. The bridge exposes only two tools, but a hostile job listing reaches a model that may have more; the app cannot see or restrict that.
- **Why it is yours:** It is your ChatGPT account and privacy settings, and the residual risk is yours to accept.

### D9. Run Phase 0 first and accept a stop if it fails.

- **Options:** Yes: 2-3 days of experiments before any app code (recommended) | No: build Phase 1 directly and treat it as the experiment
- **Recommendation:** Yes. The spike's 0 blocks in 32 writes used fake data with no emails, phones, URLs or currency, at 14-15 KB, with 6-char codes; real payloads are 18-65 KB, PII-heavy, with 24-char mixed-case codes, over OAuth, which was never tested.
- **Why it is yours:** It spends calendar time and accepts that the project may be cancelled on evidence.

### D10. Bug-report telemetry for the bridge (counts, enums, timestamps, last error code; no prompts, codes, ids or URLs).

- **Options:** Yes, in Phase 2 | No
- **Recommendation:** Yes; without it a report cannot tell whether a round came from the bridge or a paste (the lifecycle receipts have no transport field).
- **Why it is yours:** It changes what leaves your machine inside copied bug reports, even in redacted form.

## 5. Architecture

TOPOLOGY
ChatGPT (ordinary Chat, macOS desktop app; plugin created once on the web) -> OpenAI connector egress -> Cloudflare edge (Jack's zone; WAF skip rule for /mcp, /oauth/*, /.well-known/*) -> cloudflared (Jack-run launchd agent; ingress: hostname -> http://127.0.0.1:43193 with a catch-all 404; a unix-socket origin in a 0700 directory is preferred if Phase 0 shows the installed cloudflared supports it, because it removes local port-hijack) -> loopback listener in Electron main, bound ONLY while a session or pairing window is open -> http.js -> mcp.js / oauth.js -> engine.js -> source adapter -> getLocalApplicationHandoff / submitLocalApplicationHandoff / localApplicationStatus.
Renderer: HandoffBridgePanel (pill + popover) subscribes to the existing cross-tree dock store (subscribeApplicationHandoffs, src/utils/applicationHandoffDock.js:436), sends main only {jobId, canvasFilePath, label} for the jobs Jack ticks at Start, and turns main's 'handoff-bridge:application-changed' events into requestApplicationHandoffRefresh(jobId) (applicationHandoffDock.js:559) so the dock re-reads in milliseconds instead of its 20 s discovery interval (src/hooks/useApplicationHandoffDock.js:29). No dock edits.

MODULE MAP (all new; none are pinned by source-text tests) - electron/ipc/handoffBridge/:
- index.js controller: registerHandoffBridgeHandlers({notify, getCanvasWindows}), pairing window, start/stop session, kill, quiesce, status snapshot. Idempotent, memoizes in-flight start (applicationSync.js pattern), never throws to callers, returns fixed reason codes, refuses to arm under INFINITE_CANVAS_E2E / isBackgroundE2E() and unless app.isPackaged (or INFINITE_CANVAS_HANDOFF_BRIDGE_DEV=1); env INFINITE_CANVAS_HANDOFF_BRIDGE=0 hard-disables.
- http.js: the only code that touches untrusted bytes. createRequestHandler(port) returns (req,res) so tests bind no port. Routes: POST /mcp; GET /.well-known/oauth-protected-resource (and the /mcp-suffixed form), GET /.well-known/oauth-authorization-server; GET/POST /oauth/authorize (pairing window only); POST /oauth/token; POST /oauth/register only if Phase 0 proves ChatGPT needs DCR. Everything else: uniform 404 before any body is read. Host header must equal the configured hostname; 2 MiB body cap; header/request timeouts; per-source and per-token rate buckets evaluated BEFORE parsing; no CORS; Cache-Control: no-store; closeAllConnections() on stop.
- mcp.js + tools.js: JSON-RPC subset and the frozen tool descriptors/wording constants. Tolerates tools/call with no preceding initialize, answers unknown methods (server/discover) with HTTP 400 + -32601, GET/DELETE with 405, JSON-RPC batch arrays with -32600 (all as observed in RESULTS.md:25,57 and spike server.js). Stateless, plain-JSON replies.
- oauth.js (pure, injected store) + store.js (the only fs user).
- engine.js (pure, injected clock and ports): session, chat epoch, lanes, code index, single-flight, verdict cache, tombstones, caps, waiting logic, budgets, telemetry counters.
- preflight.js, framing.js, errors.js (fixed strings), log.js (private logger accepting enumerated codes only), audit.js (metadata ledger), power.js (optional-chained powerMonitor/powerSaveBlocker/setBackgroundThrottling).
- sources/application.js (Phase 1), sources/push.js (Phase 3). Only sources/application.js imports localAiApplication.js and only for getLocalApplicationHandoff, submitLocalApplicationHandoff and localApplicationStatus; a source-scan test asserts that, and that nothing in the directory imports nonApiAi.js until Phase 3.

PROCESS MODEL. In-process in main for v1: the engine calls in-process functions, and a second process would need a new vite entry with no packaged-runtime gate. Containment of the pre-auth surface instead: http.js, mcp.js, oauth.js, preflight.js and framing.js import only node:http, node:crypto and sibling pure modules (source-scan test: no fs, child_process, electron, eval or new Function); they reach privileged behavior only through an injected narrow port {authorize(token), get(), submit()}; bodies are parsed once into validated shapes copying only known keys (no Object.assign or deep merge of parsed input); non-string, array or oversized fields are rejected before any crypto or app call. utilityProcess is deferred on purpose: it gives crash and event-loop isolation but not privilege isolation (it is not an OS sandbox), so it would not shrink what an attacker who defeats auth can reach. Revisit if a measured stall or a security review finding says otherwise.

STATE. Memory only: session, chat epoch, lanes, code index, verdict cache, tombstones, rate buckets, pairing code, chat key. Disk (all non-reversible or non-secret): <userData>/handoff-bridge/state.json (0600, tmp+rename, serialized write chain, {version:1}, unknown version = unpaired) holding enabled, publicBase, port, the static client id and the HASH of its secret, and grants (SHA-256 of tokens with expiry, client id, resource). audit.jsonl (0600, rotate at 1 MiB, keep 2). No safeStorage: nothing at rest needs decrypting, so the Keychain and signing-identity coupling (project_signing_identity_is_load_bearing) is not touched and there is no decrypt-failure trap (settings.js:57-77 returns '' and memoizes the failure). Nothing in electron-store (get-settings returns the whole store to the renderer, reader-cited settings.js:161-212) and nothing in node.data (no versioned migration).

MAIN.JS HUNKS (all additive): (1) import; (2) registerHandoffBridgeHandlers() inside try/catch after registerNonApiAiHandlers() (main.js:1178), because a synchronous throw inside the whenReady callback would skip createWindow (main.js:927-943 warning); (3) stopHandoffBridge() as a fourth entry of the quit Promise.allSettled (main.js:1361-1365, inside the 25 s race). No startup hunk: the bridge never starts by itself. The background-E2E cleanup helper and its regex-pinned block (scripts/tests/electron-regressions.js:115; electron/utils/backgroundE2e.js:33-45) are untouched because the bridge refuses to arm under E2E.

PRELOAD (additive one-liners after :196): handoffBridgeGetStatus, handoffBridgeSetEnabled, handoffBridgeOpenPairing, handoffBridgeStartSession, handoffBridgeNewChat, handoffBridgeContinueMessage, handoffBridgeHold, handoffBridgeStop, handoffBridgeDisconnect, handoffBridgeHint, plus createListener subscriptions onHandoffBridgeStatus and onHandoffBridgeApplicationChanged. NO SECRET CROSSES IPC: the chat key, pairing code and client secret are shown or copied by main (native dialog; clipboard.writeText in main), so the renderer, which has no CSP and no sender-frame checks (grep of electron/ and index.html finds none), never holds them.

## 7. Queue integration

APPLICATION BUNDLES (PULL transport; Phase 1; zero edits to localAiApplication.js). Verified facts this rests on: getLocalApplicationHandoff and submitLocalApplicationHandoff are plain exported async functions serialized per job by withLocalAiJobMutationLock and need no IPC sender (localAiApplication.js:3863-3879, 3959); the IPC handlers merely wrap them (handleSafe at ~9935-9938, reader-cited); a job has exactly ONE open handoff and stage N embeds accepted earlier stages, so there is nothing to prefetch and jobs never contend; an accept rotates the code and returns the next stage inline (4321-4349); a rejection keeps the same code, but a completion-time host-validation rejection rotates it (4270-4318).

MEMBERSHIP. The session's job set is fixed at Start from what Jack ticked in the panel (max 10, the dock cap APPLICATION_HANDOFF_LIMIT, applicationHandoffDock.js:33). Main does not enumerate disk (discoverLocalApplicationJobs returns orphans and no status, 9845-9898) and does not depend on a renderer-published manifest for membership, so the renderer unmounting the dock (its hook publishes [] on cleanup, useHandoffDock cleanup, reader-cited :287) cannot make the queue look empty. The renderer only sends wake-up hints ({jobId}) when a session job's dock item changes. canvasFilePath is renderer-reported (main.js:1197-1200), so it is NOT a trust boundary; real containment is assertRealJobDirectory plus assertManifestCanvasOwnership inside get/submit (localAiApplication.js:3652-3667) plus the native Start confirmation that lists the canvas file names.

LANE PHASES (main-owned, memory only): awaiting (an open handoff exists), host (completed/paste-completed/importing: the app is rendering, measuring, saving), done (localApplicationStatus 'saved', including the receipt path, 8875-8896), needs_user (integrity fault, 'failed', 'render-retry-required', rejection or review-round cap, host lane silent > 10 min), held (Jack took over, or a non-bridge advance was detected), gone (folder discarded: confirmed by status, never by message text).

GET. Depth-first: the current lane if still awaiting, else the next session lane in order. Read via getLocalApplicationHandoff, single-flight per lane and raced against an 8 s watchdog (the call takes the per-job lock, which an import holds for the whole render, 9256-9259, so a busy lane answers 'busy' and the next lane is tried); a 15 s snapshot cache is invalidated by own submits, renderer hints and any stale outcome. {completed:true} -> lane host. Serve handoff.prompt verbatim plus handoff.corrections when present. Get is idempotent. Never serve a lane while held.
WAITING AND queue_empty. Completion is NOT terminal: after the last accepted review the job is 'paste-completed' and import, PDF measurement and save are renderer-driven; a measured-fit failure rewrites manifest.status to 'queued' with a fresh code and returns to review (import path, localAiApplication.js:9585-9631). While any lane is host, get holds up to HOLD_MS polling localApplicationStatus (lock-free, but it can write feedback and end integrity-faulted jobs, so it is 'lock-free', not 'side-effect-free') per host lane every 4 s (single-flight), also woken by renderer hints. status 'queued' -> read and serve; 'saved' -> done; 'failed'/'render-retry-required' -> needs_user; 'invalid'/'revision-required' -> a rate-limited single-flight get (the recoverers at 3723 and 3789 are crash-recovery paths whose ONLY call site is getLocalApplicationHandoff, 3867-3868; harmless to kick). queue_empty requires every session lane done; needs_user summarizes counts only. The bridge never calls importLocalApplicationJob (senderId-bound save capability, ~9767) and never writes manifest.json, paste-draft.json, fit-feedback.json or result.json.

SUBMIT (how it re-enters the shared validation/correction path). Steps: (1) session gate; (2) size cap 1,000,000 bytes (the app cap, localAiApplication.js:58); an object response is stringified. (3) Route by the CODE ARGUMENT via the lane's served-code index (bounded 16); never by response.jobId, because the app's echo check compares response.jobId to the folder's own id and is the guard against a wrong-job answer when look-alike jobs share a chat (3248-3251). (4) PRE-CHECK, no app call: parse with the same single-fence rule (one ```json fence allowed) and JSON.parse; parse succeeds -> top-level jobId, stage and handoffCode must be present (else junk), jobId must equal the lane's (else misrouted), stage must equal the served stage (else superseded); parse FAILS -> pass to the app if the text is >= 64 chars with a brace (a real attempt gets the app's own truncation/syntax diagnostics), else junk. Why: every response that reaches the app and fails is state-mutating: it bumps the escalation streak (deleting it when no check id is named), appends a Paste Rejections.json row and REPLACES the job's remembered corrections and sidecar (localAiApplication.js:3984, 4100, 4135, 4142, 2187-2204, 2496-2502), and the spike model sent '{}' twice (RESULTS.md:40). A bridge-side fingerprint of accepted responses (>= 400 chars, same rule as the dock guard, src/utils/pasteIdentityGuard.js) blocks the same accepted text arriving for a different lane. Values (handoffCode echo, baseHashes) are NOT compared here; the app grades them and tolerates a retired echoed code (3252-3264, MAX_PRIOR_PASTE_HANDOFF_CODES=8 at 717-730). (5) single-flight and verdict cache keyed sha256(code + response), 60 s: an identical retry attaches to the in-flight call or replays the verdict instead of re-running validation (which would double-count the rejection streak). (6) call submitLocalApplicationHandoff({jobId, canvasFilePath, handoffCode, response}) under a 90 s watchdog: this is the same function the IPC handler calls, so the stale-code gate (3963-3971), parsePasteResponse, validatePasteResponse and the batteries, correction memory and escalation after three same-check rejections, review delta rounds, completion-time host validation and the atomic manifest commit all run unchanged. (7) Map the result: accepted && !completed -> next handoff from result.handoff inline; accepted && completed -> lane host, next chosen without long-polling; !accepted -> rejected with the app's validationErrors, correctionPrompt and the code in result.handoff (it can be NEW); ANY throw -> re-read with getLocalApplicationHandoff instead of matching message text (the stale throw at 3971 is a plain Error with no code): fresh code differs and fresh stage equals the response's stage -> retry once with the fresh code (the envelope, stage and baseHashes gates still guard a truly stale answer); differs and stage differs -> superseded; error.code === 'LOCAL_AI_JOB_INTEGRITY' (pasteApplicationAssembly.js:69; NOT isJobIntegrityFault, which is exported by pasteApplicationAssembly.js:88, not by localAiApplication.js) -> needs_user with a FIXED sentence, because the app's message embeds observation text from arbitrary errors (pasteApplicationAssembly.js:77-84,108-116); ENOENT -> confirm with localApplicationStatus (saved / gone / transient); anything else -> retry (identical bytes retained, resubmitted once). (8) After any bridge-caused change main sends 'handoff-bridge:application-changed' {jobId}; the panel calls requestApplicationHandoffRefresh(jobId).
CAPS. Per JOB (not per revision, because a host-validation rejection increments revision, 4287-4289): 6 validation rejections including rotated-code ones -> held with needs_user; 5 consecutive junk -> held; 8 accepted 'revised' review rounds per session -> held. Commit failures, timeouts and retries are not counted. Reset on an accepted non-final stage.
HUMAN vs BRIDGE. Both converge on the same per-job lock and code gate; the human wins. A non-bridge advance seen while a lane is awaiting (code changed, no bridge accept) auto-holds the lane ('answered in the dock; ChatGPT stopped serving it', Resume serving button). A bridge accept unlinks the human's paste-draft.json (4323) and the dock adopts the disk draft on a code change (NonApiAiDialog.jsx ~900-905), so the panel and runbook say not to type into a chip ChatGPT is driving; the box is NOT disabled. The dock never renders the stale-code error for application items (pre-existing gap, NonApiAiDialog.jsx:591-593, reader-cited).
SESSION BUDGET. Bytes served plus received per chat epoch; past the soft budget the current job is finished and the next get returns session_full (job boundary); past the hard budget it ends mid-job and the next chat resumes with the full prompt plus corrections. Values are provisional (my estimate: a minimal 4-stage job is ~150-250 KB through the chat) and are set from Phase 0 degradation measurements.

PUSH (requestNonApiAi; Phase 3, optional). requestNonApiAi cannot be called from main: it throws without an IPC sender context (nonApiAi.js:1975-1981), pendingRequests is a private Map, and the accept body is an anonymous ipcMain closure whose only caller identity is event.sender (2386-2391); Electron has no public way to invoke a registered handler. AUTH: OAuth 2.1 IN THE APP + A PER-CHAT SESSION KEY. ChatGPT cannot send a static bearer token, API key or custom header (reader-reported OpenAI docs; consistent with RESULTS.md:55), so the real options are OAuth or a secret inside the URL/arguments; a secret path leaks through URL logging and grants everything to whoever holds it, so it is NOT used for real career data.
1. Endpoints (only while a session or pairing window is open): RFC 9728 metadata, RFC 8414 metadata (S256 only, grant_types authorization_code + refresh_token, scope 'handoff', authorization_response_iss_parameter_supported true; offline_access not advertised), /oauth/authorize, /oauth/token.
2. Client: ONE pre-registered confidential client (id and secret generated in-app, secret stored only as SHA-256, copied once by main via the clipboard) if the Pro create-app dialog exposes static credentials; otherwise DCR, accepted only inside a pairing window, max 5 clients, redirect URIs limited to https://chatgpt.com forms, client_secret_post for confidential clients. CIMD is deferred unless Phase 0 shows ChatGPT insists (it needs SSRF-safe fetching). Which form ChatGPT uses is a Phase 0 measurement (reader reports both https://chatgpt.com/connector_platform_oauth_redirect and per-connection https://chatgpt.com/connector/oauth/<id> redirect forms).
3. Code flow: PKCE S256 only, auth code 60 s single-use, exact redirect_uri match against what was registered, `resource` bound to the canonical MCP URL at authorize (absent -> canonical, logged) and taken from the grant on refresh (absent accepted, mismatch rejected), iss on every authorization response, refresh token issued even without prompt=consent (ChatGPT is reported to send offline_access without it; an AS that skips the refresh token forces hourly re-login).
4. Tokens: opaque 256-bit, SHA-256 at rest. Access 60 min; refresh idle 14 d, absolute 90 d; rotation with a 60 s predecessor grace (a lost /token response or two concurrent refreshes replay the same successor pair); reuse OUTSIDE the grace revokes that grant and raises an alarm, but does not by itself end the session.
5. CONSENT IS BOUND TO THE MAC, NOT TO THE PUBLIC ORIGIN. 'Connect ChatGPT' opens a 10-minute, single-use pairing window. Main shows a native dialog with a one-time 10-character pairing code (50 bits), the hostname, and (static client) buttons that copy the client id and secret via main. ChatGPT sends Jack's browser to /oauth/authorize; that public page (static, no external resources, CSP default-src 'none', frame DENY, no-store, no-referrer) asks for the code. Only someone who can see the Mac's screen can type it; five wrong attempts close the window. One pending authorize at a time. This reverses the 'compare two codes' direction, so an attacker who knows the hostname and races the window cannot approve themselves, and it needs no per-request native dialog that could be flooded.
6. CHAT KEY (per chat epoch, 10 chars from the 32-char no-ambiguity alphabet, 50 bits, minted by main, embedded in the starter message, memory only, rotated by New chat). Required on every tools/call and compared in constant time. This fixes the security-first design's false claim that a ticket made a stolen token useless: with OAuth alone, any token holder could fetch every released prompt during an armed window; now a stolen token, or an injected chat that never received the starter, gets 'unauthorized'. 10 wrong keys within 5 min WITH a valid token ends the session (credential-attack evidence). Anonymous 401s never affect a session.
7. Storage: hashes only, 0600 file, no safeStorage. Nothing secret is ever put in a URL path, so cloudflared or bug-report URL redaction (origin+pathname, bugReport/helpers.js:13-37, reader-cited) cannot leak one.
IF PHASE 0 SHOWS OAUTH CANNOT BE MADE TO WORK on this account (dialog, desktop carry-over, refresh, or unreachable-AS behavior): first try always-on OAuth routes (only /.well-known and /oauth/token stay up while unarmed) or Mixed mode; if that still fails, the only remaining option is a capability URL plus the chat key plus armed sessions, which is a deliberate downgrade from RESULTS.md:55 that only Jack may accept in writing (decision 3); the default recommendation is to stop and stay on paste.

## 9. Lifecycle and failure handling

STATES: off -> ready (enabled, paired, idle; NO listener) -> pairing (10 min) -> session (listener + idle/hard timers) -> ready. Nothing auto-arms and 'armed' is never persisted.

START. Panel 'Start ChatGPT session' -> main validates the job list (UUID jobIds, absolute paths, <=10, labels sanitized to 60 chars) -> main-owned native confirm (dialog.showMessageBox on the sender's window, Cancel default): 'Send N job(s) to ChatGPT via <host>? This shares each job's listing, your career data and the drafts with ChatGPT through Cloudflare' with the jobs and canvas file names -> bind 127.0.0.1:port (or unix socket) -> self-probe the public /.well-known/oauth-protected-resource (distinguishes 'probe rejected by edge' from 'tunnel down' from 'ok') -> fail closed with a fixed reason code on any failure (EADDRINUSE, no publicBase, unpackaged build, E2E) -> copy the starter message. Adding jobs later needs another native confirm.

END. Stop, idle 30 min sliding (10 after queue_empty/paused), hard 2 h wall-clock deadline, system suspend, quit, or credential-attack evidence (refresh reuse outside grace; 10 wrong chat keys with a valid token; repeated wrong client secret at /token). Deadlines are absolute epoch times compared on EVERY request (libuv timers do not count macOS sleep), timers are belt-and-braces, no tool call ever extends past the hard cap, and queue_empty ends the useful window. Teardown order: refuse new RPCs -> await in-flight get/submit up to 10 s (a commit point is never aborted) -> close listener and connections -> clear memory state -> audit. Quit: stopHandoffBridge() in the quit allSettled (main.js:1361-1365) does the same inside the existing 25 s race. Windows are destroyed first at quit (1340-1349) but pull accepts do not depend on windows, so an in-flight accept completes.
KILL. 'Stop' (pill, popover, Settings) ends the session and clears lanes; 'Stop and disconnect' also wipes grants and the static client secret. Honest wording in the UI: Stop ends new transfers; data already sent stays in that ChatGPT chat (delete it there); deleting the plugin in ChatGPT is not revocation. A Force Quit or crash leaves no listener (the app spawns no process and holds no port after death). Remote kills: delete the tunnel in Cloudflare, Disconnect in the app. Env INFINITE_CANVAS_HANDOFF_BRIDGE=0 hard-disables.

SLEEP/WAKE. powerMonitor is optional-chained (the test stub has none, scripts/test-stubs/electron.mjs:138-141; no powerMonitor or powerSaveBlocker exists anywhere in electron/ or src/). 'suspend' ends the session; 'resume' never re-exposes; screen lock does not end it (the idle cap bounds it). While a session is live, webContents.setBackgroundThrottling(false) is applied to canvas windows and restored at end, because production windows keep backgroundThrottling true (main.js:569) and every post-completion step (status poll, import, PDF fit, reopen, dock refresh) runs on renderer timers while ChatGPT is frontmost; whether throttling actually bites is a Phase 0 measurement. powerSaveBlocker('prevent-app-suspension') only while a handoff is outstanding is Phase 2 and must be measured, not assumed.

BLOCKED / STALLED WRITES. A ChatGPT safety block never reaches the server (RESULTS.md:15-16,43-50), so the only observable facts are 'served at T, no call since' (and a dead tunnel looks the same, which is why the tunnel probe below exists). Nothing is consumed by a serve, get is idempotent, so a retry in the same chat or a fresh chat resumes exactly. UI wording states observations only: 'ChatGPT was given this 6 min ago and has not submitted since. It may still be writing, may have been blocked, or the chat was closed.' Threshold 4 min (slowest legitimate step observed ~1m50, RESULTS.md:23; tune from data). Actions: Copy 'continue' (same chat), Take over, Wait. Never labelled 'blocked'. After 2 stalls in an hour the panel suggests the paste route. Expect the first ~25 min after any plugin creation or edit to be riskier.
TUNNEL HEALTH. While a session is live with an outstanding handoff, probe the public URL every 60 s: 3 failures -> banner 'tunnel unreachable' (observed fact) and the session ends after 10 min unreachable.
RE-AUTH. Access expiry refreshes silently. Refresh failure or revocation -> ChatGPT prompts to re-link; the panel shows 'ChatGPT link needs renewing' with Connect ChatGPT. If ChatGPT drops the link whenever the origin is unreachable, fall back to always-on OAuth routes (Phase 0 E1).
RESTART/CRASH MID-SESSION. Session, key and lanes are memory-only and end; job state is durable. The model's next call gets 'unauthorized' (or session_ended if the key hash survived in memory); Jack presses Start and 'Continue' or 'New chat'. Accept-path crash window: the app appends the Generation Log BEFORE the atomic manifest write (localAiApplication.js:4326 then 4328); a crash between them followed by a DIFFERENT resubmission throws 'already contains a different event for this sequence' (3545) and wedges that stage, while an identical or key-order-equivalent resubmission recovers (3544, canonicalLogJson). Bridge mitigation only: retain the exact submitted bytes per (job, code) and on any throw whose re-read shows the SAME code resubmit those identical bytes once before answering retry; needs_user if that throws too. The app-side fix (recover when manifest.logCount is behind the log tail) is a separate change and Jack's decision; it is equally reachable by a human paste, only slightly likelier with an unattended retrying model.
CONCURRENCY AT TEN JOBS. Data level: state is per job under per-job locks; push records use record.settling; I found no corruption path. Practically the bridge is single-chat serial: ten jobs are ~5 chats at ~2 jobs per chat budget and on the order of 100+ minutes (spike pace ~30 s per handoff, first resume 1m38-1m50, RESULTS.md:23; real payloads are larger, so this is a lower bound), each new chat needing one starter paste. Imports are serialized across jobs (reader-cited useLocalAiFallbackManager.js:66-67); validation runs synchronously on main, so a semaphore of 2 concurrent submits protects the UI; both are unmeasured. Parallel chats are not offered in Phase 1: a second starter rotates the key and fences the first chat, which is what prevents duplicate dispatch. Pasting the same starter into two chats without New chat is unsupported; the panel shows 'served 2x, nothing submitted' as the observable warning.
OTHER RACES. Discard racing a served job: ENOENT is confirmed via localApplicationStatus (saved receipt / failed / transient), then the lane goes gone; a submit that started before discard runs under the job lock while discard uses a prune claim, not that lock (8811-8859, reader-cited), so Take over and Discard wait for the lane's in-flight promise. Window closed or canvas not open: host lanes cannot complete; after 10 min unchanged they become needs_user with an observed-fact message ('the app has not advanced this job in 10 min; is the canvas open?').
ERROR TEXT. Every outcome is mapped by error.code or class to a FIXED bridge-authored sentence. error.message, stack, localJob (absolute folder path) and the app's integrity observation (arbitrary text, pasteApplicationAssembly.js:108-116) are never forwarded; validationErrors and correctionPrompt (app-authored, about the caller's own response) pass through with absolute-path-looking substrings scrubbed.

## 10. Security

THREAT MODEL SUMMARY. Copy/paste has no inbound surface. The bridge adds (1) an Internet-reachable listener next to a privileged main process (marketplace/browser logins, process spawning, no CSP, no sender-frame checks in IPC), (2) a third party (Cloudflare) in the plaintext path, (3) durable credentials, and (4) an unattended model loop over untrusted third-party text. Controls, each with a test:
T1 EXPOSURE. Listener exists only while a session or pairing window is open; never persisted, never at launch; ends on Stop, idle, wall-clock hard cap (checked per request), suspend, quit, or credential-attack evidence. Because the app spawns nothing, S2-type guarantees hold after a crash or force-quit (no orphan tunnel). Route allowlist with uniform 404 before any body read; Host must match the configured hostname; body cap 2 MiB; header/request timeouts; per-source and per-token rate buckets evaluated before parsing (unauthenticated junk cannot consume the authenticated budget and never disarms a session: a remote stranger must not hold a kill switch). Optional edge allowlist of OpenAI's published ranges (see publicUrlAndAuth). Presence oracle: any public endpoint reveals 'a session is armed' (listener exists); accepted, since PRM must be public; unauthorized results are uniform.
T2 AUTHENTICATION. OAuth 2.1 (S256, resource-bound opaque tokens hashed at rest, refresh rotation with 60 s grace) plus the per-chat key; pairing consent requires typing a code that only appears on the Mac. The refresh-reuse alarm revokes the grant. The hand-rolled AS gets a dedicated security review (/security-review skill) and a negative-test battery BEFORE any real data crosses it.
T3 DATA MINIMISATION. Whitelist projection only; prompt served verbatim; no jobId, paths, localJob, draft or scraped labels in bridge-authored fields; attachment, grounded, marketplace, price and account-derived tasks are never served (push allowlist is default-deny). Job set fixed at Start.
T4 CONSENT. One main-owned native confirmation per session (and per addition) naming jobs, canvas and destination; a renderer script alone cannot start egress (the renderer has no CSP and IPC has no sender-frame checks). The renderer never holds the chat key, pairing code or client secret.
T5 KILL. Stop / Stop and disconnect from the pill and popover; Quit is a full kill. Honest scope: data already delivered stays in ChatGPT history; the plugin deletion in ChatGPT does not revoke tokens.
T6 PROMPT INJECTION. Job-listing text is third-party content inside an instruction-bearing tool result in a model that may also have browsing, memory or other apps. This is materially larger than paste because the model runs unattended and get_handoff returns other jobs' prompts. Controls: rules live in the tool descriptions (developer-level trust) and the starter message, not only in results; the tool description bars every other tool, links and memory; no scraped string appears in any bridge-authored field; application prompts embed listing text inside JSON.stringify(context) so it cannot break structure (localAiApplication.js:1246); the chat key means an arbitrary injected chat cannot fetch; hostile-canary gate in Phase 0 (a synthetic listing that tells the model to open a URL, call another tool, or reveal the key must be ignored in 3 of 3 fresh chats). Not enforceable by the app: other tools in the same chat are an exfiltration channel. Jack must use a dedicated ChatGPT Project with memory, browsing and other apps off (decision 8). The panel states this plainly instead of implying protection.
T7 LOGGING AND BUG REPORTS. A private logger that takes enumerated codes only (no free-string parameter); a source-scan test bans .message, .stack and req.url inside the directory (V8 JSON.parse errors quote body fragments; applicationSync logs error.message, applicationSync.js:1098); every parse goes through one function that throws a fixed-code error; hostname added to bug-report URL redaction (which keeps origin+pathname); sentinel-string tests over logs, telemetry, status and the audit ledger including parse-error and tunnel-probe paths. Handoff codes, chat keys, job ids and labels are never logged.
T8 SECRETS AT REST. Hashes only in a 0600 file; no safeStorage (no plaintext fallback like settings.js:42, no decrypt-failure invalidation); nothing in electron-store or node data; the file is not returned by any IPC.
T9 PROCESS. Pre-auth code is narrow and import-restricted (see architecture); in-process for v1 with utilityProcess deferred (no privilege gain); JSON parsed into validated shapes, prototype-pollution and deep-nesting cases in a fuzz table test.
T10 TUNNEL TRUST ROOT (Jack's side). Cloudflare account/zone/registrar compromise or the local credentials file lets an attacker attach a connector to the hostname and receive a share of requests. Mitigations are runbook items (delete cert.pem, dedicated account with hardware-key 2FA, 0600 credentials, no token in argv, log hygiene) and the fact that a captured bearer still lacks the chat key and only works while a session is live; rotate/Disconnect after any Cloudflare-side change.
INTEGRITY. A stolen token plus key during a live session could read the current prompt and submit a poisoned but validator-passing answer; the app's grounding validators and Jack's review of the finished application bound the impact, and the audit ledger records source class (HMAC of the source address, Cloudflare vs unexpected) with each serve so an out-of-range caller raises a panel alarm and ends the session.
GET ANNOTATION. get_handoff is declared readOnlyHint true (spike-proven) although the underlying read can write idempotent host recovery; compensated by the chat key; A/B tested in Phase 0.
ACCEPTED RESIDUALS (stated, not hidden): Cloudflare reads plaintext; hand-rolled OAuth is inherently risky code (mitigated by review and tests); ChatGPT-side retention of connector payloads is not determinable from the repo (Phase 0 checklist: improve-the-model off, memory off, delete chats); a hostile listing can still influence the model.

## 13. Why this design over the alternatives

WHAT EACH DESIGN CONTRIBUTED. From minimal-transport: zero edits to the two huge source-pinned files in Phase 1, hand-rolled MCP, an external tunnel, the frozen two-tool surface, the bridge-side junk filter, a Phase 0 gate on realistic payloads, and 'human always wins'. From robust-relay: the status vocabulary and idempotent lane/tombstone/verdict-cache discipline, the attempt cap with hand-back, wire-protocol tolerance from the spike log, and the frozen-metadata rule. From security-first: armed-only exposure, native-first consent, a kill switch, metadata-only egress ledger, hashed tokens with no safeStorage, source-scan import allowlists and sentinel privacy tests, and deferring the risky push hoist.
WHY NOT THE OTHERS AS WRITTEN. Minimal used a path secret plus session code: fine for fake data, and the task states real prompts need real auth (RESULTS.md:55), so OAuth replaces the secret path. Relay adds a cloud root of trust and ~1,000 lines for a benefit (OAuth alive while the Mac sleeps) that a pull model with a renderer-driven completion loop barely uses; see rejectedAlternatives. Security-first had the right posture but a false headline (tickets) and an app-spawned tunnel with orphan, certificate and config-injection problems.

HOW EACH BLOCKER/MAJOR FINDING IS RESOLVED
Security/privacy (all three designs' critiques):
- Remote caller could hold the armed window open (relay), and unauthenticated noise could disarm (security-first, integration): deadlines are absolute wall-clock times checked per request, no call extends past the 2 h hard cap, idle extends only on authenticated calls carrying the chat key, and a session ends only on credential-attack evidence (refresh reuse outside grace, wrong keys WITH a valid token, wrong client secret); anonymous 401s never affect a session; limits are per source and per token before parsing.
- Token alone can read everything (security-first): per-chat key required on every call, rotated by New chat; unauthorized results are uniform.
- Scraped text in trusted frame fields and forgeable END marker (minimal, relay): default result is JSON with the prompt as a string value; no scraped string in any bridge-authored field; nonce markers only if the plain-text frame wins the Phase 0 A/B.
- Injection stance understated, no canary (all): rules in tool descriptions, tool-scope ban, chat key, allowlist, Phase 0 hostile-canary gate, honest UI wording, decision 8.
- Raw exception text leaks (minimal): fixed-string mapping by error.code/class, path scrubbing of validationErrors, fault-injection tests (integrity observation embeds arbitrary text, pasteApplicationAssembly.js:108-116).
- Real data through the least-hardened config (minimal): every privacy control is a Phase 1 exit criterion; synthetic data until then; separate lab hostname.
- Tunnel trust root, cert.pem, log leakage of a secret path (minimal, security-first): no secret in any URL; runbook for cert.pem, credentials, 2FA, log config; Cloudflare-side risks are in decision 1 and 2.
- safeStorage contradictions and self-destroying URL (minimal, relay): no safeStorage at all; hashes at rest.
- Consent binding weaker than claimed (relay, security-first): typed pairing code that only appears on the Mac; single pending authorize; native Start confirm; renderer never holds secrets.
- Desktop trusts relay (relay): no relay.
- Renderer can arm with no gesture; canvasFilePath is renderer-declared (all): native confirm at Start and per addition; containment is assertRealJobDirectory plus ownership checks, not window paths.
- In-process parsing of hostile bytes (security-first): narrow import-restricted layer with a port boundary and fuzz tests; utilityProcess deferred with the stated reason.
- No security exit gate; lab no-auth path on the real hostname (relay): /security-review and the negative battery are Phase 1 exits; lab hostname separate.
- S1/S2 false after crash/force-quit (security-first, integration): the app spawns nothing; the listener dies with the process.
- Network restriction deferred to Phase 4 (security-first): Phase 0 measures sources in log mode; edge allowlist for /mcp and /token enforced in Phase 1 if measurable, source-class alarm otherwise.
Integration/reliability:
- Bridge skips the dock identity guard (minimal): bridge pre-check (jobId, stage, accepted-fingerprint) with no app call; the correction text says the bridge gets host validators only.
- queue_empty derived from a renderer manifest that is legitimately empty on unmount (minimal, relay): membership fixed at Start, per-lane terminal evidence from localApplicationStatus, never queue_empty on an empty publish.
- Two writers on one lane / duplicate dispatch (minimal, relay, security-first): one active chat per session, New chat rotates the key, auto-hold on a non-bridge advance.
- Rejection cap keyed by revision cannot fire (minimal): per-job counters including rotated-code rejections, junk cap, review-round cap.
- Quit does not drain an in-flight submit (minimal, relay): stop() refuses new RPCs and awaits in-flight calls up to 10 s inside the quit race.
- Renderer background throttling (minimal, relay): setBackgroundThrottling(false) during a session plus a Phase 0 measurement; lane state is read by main independent of renderer cadence where possible.
- Session budget deferred while sizes overflow it (minimal, relay): budget in Phase 1, cut at job boundaries, values from Phase 0.
- Tombstones keyed by code alone (relay): keyed by (job or request, code), consulted after the live registry.
- Hoist returns collapsed outcomes (relay): internal reason enum from a phase variable, IPC shape unchanged.
- Leased UI disables the paste box (relay): the box is never disabled.
- No single-flight between relay deadline and main work (relay, security-first): per-lane single-flight, 8 s get race, 90 s submit watchdog, verdict cache so a retry attaches to the in-flight call.
- Refresh reuse without grace, and noisy limits (security-first): 60 s grace; alarm and grant revocation, not session kill.
- Post-completion watcher cannot drive reopens (security-first): corrected (see corrections); low-rate get kick on invalid/revision-required.
- Warm-up experiments destroy the state they measure, and Phase 0 omits platform ceilings (relay, security-first): disposable second plugin for reset tests; E4 measures ceilings; frozen surface after Phase 0.
- Stale-code throw discards valid answers (security-first): re-read and retry once when the stage matches; superseded otherwise.
- Bridge-side junk filter applied to push and to free-text tasks (minimal): scoped to applications and structural; push rejects only empty, whitespace, '{}' and '[]'.
- Crash-gap wedge (all): identical-bytes resubmit in the bridge; separate app fix is decision 7.

REVERSIBILITY. Phase 1 adds inert-by-default new files, three guarded main.js hunks, additive preload and UI lines, and no schema, settings or node-data change. Turning the toggle off or setting the env var means the module never binds a port; deleting the directory and the hunks restores today's app exactly.

## 14. Rejected alternatives

1. Worker + Durable Object relay with the desktop as an outbound WebSocket client (robust-relay design). Rejected for v1: in a pull model the Mac must be awake with a live renderer anyway (completion is renderer-driven), so its headline benefit, OAuth staying up while the Mac sleeps, is unproven to matter; it adds a public cloud component that becomes a plaintext root of trust, ~1,000+ lines of Worker code, device enrollment and signing, WebSocket heartbeat, a second deployable and its own security critiques (remote caller can hold the armed window, relay-supplied approval frames, no independent grant check). Reconsider only if Phase 0 shows ChatGPT drops the OAuth link when the origin is unreachable, or unattended serving becomes a goal.
2. App-spawned cloudflared (security-first design). Rejected: orphan tunnel after a crash or force-quit (no PDEATHSIG; process.on exit does not run on a crash), cert.pem/credentials handling, YAML config injection from renderer-entered strings, GUI-launch PATH lookup, inheriting process.env secrets, and a binary to trust or sign under the pinned identity.
3. Secret path in the URL as the only auth (the spike's /mcp/<token>). Rejected for real data: URLs are logged by proxies and the bug-report redactor keeps origin+pathname, and possession of the URL grants everything.
4. A ticket alias for routing (security-first design). Rejected: it did not make a stolen token useless (get mints tickets for any holder), an expired ticket discards an answer the app would accept, and the model must copy the app's 24-char code into the JSON envelope anyway. Replaced by the per-chat key plus routing by the app's own code.
5. Per-job release clicks (security-first). Replaced by one native confirmation per session that names the fixed job set; the same consent, far less friction.
6. Disabling the dock paste box while ChatGPT holds a job. Rejected: violates hard rule (c), depends on renderer state that can go stale, and the real protection is the existing per-job lock and code gate.
7. Main enumerating pending application jobs from disk with discoverLocalApplicationJobs (localAiApplication.js:9845-9898). Rejected: returns orphans of deleted cards, dismissed bundles and no status, and ignores the dock cap. Also rejected: making main depend on a renderer-published queue for membership (an unmounted dock publishes [] and would produce a false queue_empty).
8. Adopting @modelcontextprotocol/sdk, zod and ajv in the app. Rejected: new lockfile and CI weight, rolldown interop unproven, packaged runtime ungated. The SDK client is kept only as a conformance harness.
9. Using the SDK's express-based OAuth router or Cloudflare Access Managed OAuth. Rejected: the router is deprecated upstream in SDK v2 (reader-reported) and Access Managed OAuth is unverified with ChatGPT and couples the bridge to Cloudflare.
10. OpenAI Secure MCP Tunnel. Rejected: needs a Platform organization and sk- runtime key (conflicts with no-API), no published price, and two open reports say personal Pro workspaces cannot use it (reader-reported).
11. ngrok, quick tunnels and Tailscale Funnel as the default. ngrok: interstitial, low caps and a ToS clause about Customer Data. Quick tunnels: URL changes every start (RESULTS.md:54). Funnel: only third-party ChatGPT evidence; kept as the privacy-preferred alternative.
12. utilityProcess isolation in Phase 1. Deferred: crash and event-loop isolation only, no privilege isolation, needs a new build entry with no packaged-runtime gate.
13. Serving push handoffs first, or in Phase 1. Deferred to Phase 3: needs the hoist in a source-pinned file, generation time dominates, attachment and grounded tasks can never be bridged.
14. Driving the renderer's IPC from main via executeJavaScript for push submits. Rejected: couples to renderer state, re-imposes sender identity, adds a relay hop; the additive hoist is smaller in behavior risk.

## 15. Unresolved risks

1. OAuth interop is unproven for a Pro personal account: which registration form the create-app dialog offers, whether a link made on the web works in the desktop app Chat, refresh behavior, and whether ChatGPT drops the link when the armed-only origin is unreachable. The spike used No auth. Phase 0 E1 decides; fallbacks are always-on OAuth routes, Mixed mode, or stop.
2. Real payload behavior is unmeasured: PII-bearing 30-65 KB tool results and 20-30 KB arguments (the spike proved 14-15 KB with fake data lacking emails, phones, URLs and currency: verified by grep of spike jobs.js), 24-char mixed-case code copying, and whether the paste-worded real prompt still makes the model call submit_handoff instead of answering in chat.
3. Safety-block warm-up: writes were blocked within ~12 min of plugin creation and never after ~22 (RESULTS.md:43-50); it is UNKNOWN whether URL, tool or auth-mode changes or a new hostname reset it, and blocks never reach the server so the app can only observe 'served, nothing since'. Write-only block waves were reported platform-wide around 2026-09-23 (reader-reported). The paste path is the permanent fallback.
4. Chat context growth: prompts are 18-65 KB, a minimal job is ~150-250 KB through the chat, and the correction delta assumes the original prompt is still in view (localAiApplication.js:2019 per reader). The session budget values are my estimate; Phase 0 must find the degradation point. A run of hundreds of push batches cannot fit one chat.
5. Held-call tolerance, per-reply tool-call and wall-clock ceilings, and whether ChatGPT keeps polling waiting results are unmeasured; if holds are not tolerated the design degrades to immediate waiting results and more model polling.
6. Renderer-driven completion: import, PDF measurement, fit reopen and dock refresh run on renderer timers, production windows keep backgroundThrottling true (main.js:569), and ChatGPT will usually be frontmost. setBackgroundThrottling(false) during a session (API present, electron.d.ts:18403) is untested. If the app needs the canvas open to finish jobs, a closed or unsaved canvas strands work at paste-completed.
7. Import lock and main-thread load: getLocalApplicationHandoff shares the per-job lock that an import holds for a whole render (localAiApplication.js:9256-9259 per reader), imports are serialized across jobs, and validation batteries run synchronously on main while the UI shares the thread. Watchdogs and single-flight bound tool-call latency but the actual stall is unmeasured on real-size fixtures.
8. Hand-rolled OAuth and MCP code is the only parser of untrusted bytes and runs in the privileged process. Mitigated by narrow imports, a port boundary, fuzz and negative tests and a security review, but a logic bug remains possible; utilityProcess would add crash and event-loop isolation only.
9. Third parties and credentials: Cloudflare can read plaintext in transit; the tunnel credentials file (and cert.pem if not deleted) on the Mac is a root of trust; ChatGPT-side retention, memory and training treatment of connector payloads cannot be determined from the repo; the domain price and Cloudflare free-tier limits were not verified.
10. Prompt injection: a hostile listing reaches an unattended model that may hold other tools. The bridge cannot enforce Jack's ChatGPT hygiene; the canary test measures one model on one day.
11. Human-versus-bridge on one job can waste generation: the paste box stays enabled, a bridge accept unlinks the human's draft and the dock adopts the disk draft on a code change (NonApiAiDialog.jsx ~900-905), and the dock never renders the stale-code error for application items (pre-existing). Auto-hold and the panel warning reduce but do not remove it.
12. Duplicate dispatch if Jack pastes the same starter into two chats without pressing New chat: the server has no chat identity, so both get the same current handoff; only the panel's 'served 2x' fact reveals it.
13. Accept-path crash window (Generation Log append at localAiApplication.js:4326 before the manifest write at 4328; a different resubmission throws at 3545). Pre-existing, equally reachable by paste; bridge mitigation is identical-bytes resubmit only.
14. No automated gate covers the packaged runtime (smoke runs unpackaged, CI stops at build:compile). Zero new dependencies removes the bundling class of failure, but a manual packaged check is required.
15. Only one model at one effort level was ever tested (RESULTS.md:35), and the ChatGPT plugin/OAuth surface is a moving target; whether plugin tool calls count against Pro limits is unresolved (Analytics re-check outstanding, RESULTS.md:32).
16. External claims I relied on but did not re-verify (I read only the repo): OpenAI's OAuth requirements, redirect URI forms, connector IP feed, Cloudflare's macOS service docs and pricing, cert.pem permissions, unix-socket ingress, and the alleged docs/non-api-ai-handoff-id-handoff.md drift; each is either a Phase 0 measurement or labelled reader-reported above.

## 16. Corrections the synthesis made to the readers and designs

1. Coupling test in the minimal design ('imports only getLocalApplicationHandoff, submitLocalApplicationHandoff and isJobIntegrityFault from localAiApplication.js') is unsatisfiable: isJobIntegrityFault is exported by pasteApplicationAssembly.js:88, not localAiApplication.js (which only imports it, :25). Detect the fault with error.code === 'LOCAL_AI_JOB_INTEGRITY' (pasteApplicationAssembly.js:69).
2. Robust-relay and security-first designs assume a one-word export of parsePasteResponse; it is NOT exported today (localAiApplication.js:817 is a plain function). It is also unnecessary: the bridge pre-check uses its own single-fence regex plus JSON.parse and fails open to the app on any parse difference.
3. Minimal and relay designs cite settings.js:66-76 as a precedent for 'invalidate on decrypt failure'; the actual code returns '' and memoizes the failure, and never deletes or rewrites the stored blob (settings.js:57-77). Their 'safeStorage is not touched at startup' also contradicts an auto-started bridge that must decrypt its token. Resolved by using no safeStorage.
4. Security-first design claims a lease ticket means 'a token alone can neither read nor answer anything'. False: get_handoff mints and re-serves tickets to any valid token holder with no chat identity. Fixed with the per-chat key.
5. Integration critique of security-first says two of three reopen paths exist ONLY inside getLocalApplicationHandoff, so a status-only watcher stalls. Overstated: the recoverers (localAiApplication.js:3723, 3789; only call site 3867-3868) are crash-recovery paths; the normal fit reopen is written by the renderer-driven import (9585-9631, manifest status 'queued' with a rotated code) and the normal host-validation reopen is returned by submit itself (4270-4318). Status reads see 'queued' after either. The bridge still kicks get on 'invalid'/'revision-required' at a low rate, harmlessly.
6. Several designs call localApplicationStatus 'lock-free' as if that made it read-only: it can write rejection feedback (~9083) and end an integrity-faulted job (8998-9001); it only avoids the per-job mutation lock. get is the same: getLocalApplicationHandoff can end a job (3703-3707) or rewrite the manifest in the recoverers (3770-3772, 3853), so readOnlyHint true on get_handoff is a mismatch compensated by the chat key.
7. The minimal design's 'a bridge submit is validated exactly as a paste' omits the dock's pre-submit layer: assessPastedResponse lives only in the renderer (src/utils/pasteIdentityGuard.js), and on the host side a wrong-job answer is rejected only AFTER the rejection branch has bumped the streak, appended a trace row and replaced the job's corrections (localAiApplication.js:4100-4146). The bridge needs its own pre-check; the design text must say the bridge gets the host validators, not the dock guard.
8. Designs that key tombstones or code indexes by handoff code alone are wrong for push: codes are deterministic from base prompt, task, nodeId, batch and attachments (nonApiAi.js:461-472) and recur across re-runs, Back and restarts. Application codes are random (randomBytes(18), localAiApplication.js:706-708) and unique.
9. The hoisted-handler sketches return only accepted/validationErrors; that collapses five different outcomes. The current catch (nonApiAi.js:2450-2474) turns a durable-write failure into a validation rejection with error.message stored verbatim as validationError and sent to the dock, and the early returns at 2417-2419 and 2454-2456 have the same shape as a real rejection. The hoist must add an internal reason enum while the IPC return shape stays unchanged.
10. Designs that validate canvasFilePath against 'canvas files main itself tracks' treat win.__canvasFilePath as a trust boundary; it is renderer-reported (main.js:1197-1200). Real containment is assertRealJobDirectory and assertManifestCanvasOwnership inside get/submit (localAiApplication.js:3652-3667).
11. get_handoff results in the minimal and relay designs include 'JOB: <company - title>' or a label; those are scraped strings (dock label = node.data.company||title, applicationHandoffDock.js:248) and must not appear in bridge-authored fields. Also, submit's rejection branch returns pasteHandoffRecord with draft: response (localAiApplication.js:4144-4146), so handoff.draft is the rejected response and must never be served.
12. The relay design's 'quit closers with no drain' and the minimal design's 'stop() closes connections in well under a second' both ignore an in-flight accept, which is a multi-write sequence (drafts file, unlink, log append, manifest, corrections clear: 4321-4349). stop() must refuse new RPCs and await in-flight calls (bounded) before closing.
13. Reader claim that the React Compiler is 'enabled' vs 'not running': both are true in effect. vite.config.js uses plain react() (line 24) and no compiler plugin is installed; the rules are enforced at lint time by eslint-plugin-react-hooks v7 (eslint.config.js:3,20-24), which is what constrains new src/ code.
14. I did not re-verify the readers' claims about docs/non-api-ai-handoff-id-handoff.md drift (section 4.4, 'exactly 3 free-text sites'), the OpenAI and Cloudflare documentation facts, or the domain and tunnel pricing; they are carried as reader-reported and flagged where they matter. The design does not depend on the docs claims.

## 17. Verification notes (added by hand after the workflow)

- **Code claims spot-checked and confirmed** against the repo: `getLocalApplicationHandoff` (`localAiApplication.js:3863`), `submitLocalApplicationHandoff` (`:3959`), `localApplicationStatus` (`:8861`), application codes from `crypto.randomBytes(18)` (`:707`), the existing loopback listener in `applicationSync.js`, `backgroundThrottling: !isBackgroundE2E` (`main.js:569`), `isJobIntegrityFault` exported from `pasteApplicationAssembly.js:88`, `safeStorage:v1:` prefix in `settings.js`. The rest of the code citations were not individually re-verified; treat line numbers as approximate and re-check before editing.
- **One claim in the readers, the synthesis (D9, unresolved risk 2) and the workflow's own external-options reader is wrong:** that the spike's fake data lacked "currency". `scripts/chatgpt-handoff-spike/jobs.js` contains `$410k` and `$90k` and several percentages, plus fictional employer names, and all of those passed ChatGPT's safety layer. What it genuinely lacks is emails, phone numbers, URLs, real names and addresses, so the real-payload gap (Phase 0a) stands but is narrower than stated.
- **Annotation honesty for `get_handoff`.** The synthesis notes (corrections 6) that `getLocalApplicationHandoff` can end a job or rewrite the manifest on recovery paths, yet proposes `readOnlyHint: true` "compensated by the chat key". Do not ship a tool that can change state marked read-only: Phase 0 E8 should test `readOnlyHint` true versus false, and if any reachable path mutates, declare it non-read-only or split the recovery out of `get`.
